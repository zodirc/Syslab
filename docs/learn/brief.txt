# 数、调用和可执行文件
业务上先看到的是计算结果、函数返回值、动态派发和可执行文件能否启动。下面各节从这些现象往下核对：字节编码、返回值、参数寄存器、虚函数的动态类型、ELF 标识、动态加载器、原子读改写的数值，以及分支循环的校验和。

=== CPU-001
应用
序列化、网络报文和共享内存按字节保存整数与浮点。接收端读出的符号相反，或 1.0 变成其他数值时，先读取发送端内存中的字节。

原理
C++20 规定带符号整数使用补码。int 类型的 -1 在内存中每个字节都是 0xff。当 numeric_limits<float>::is_iec559 为真时，1.0f 的 binary32 编码是符号位 0、阶码 127、尾数 0，十六进制 0x3f800000。is_iec559 为假时，本节不改用推测编码。

证明
int -1 的每个字节都是 ff，与图中的四个字节一致。
numeric_limits<float>::is_iec559 为真，继续读取 1.0f 的内存。
1.0f 的符号、阶码和尾数与图中的 binary32 布局一致。

=== CPU-002
应用
函数返回的合计与调用方传入的参数之和不一致，或崩溃发生在函数返回之后。

原理
语言要求 add_six(1, 2, 3, 4, 5, 6) 的返回值等于 21。参数进入哪个寄存器属于调用约定，由反汇编观察，不作为本节的数值条件。

证明
add_six(1, 2, 3, 4, 5, 6) 的返回值是 21，与图中的返回值一致。

=== CPU-004
应用
C++ 调用汇编函数，或另一种语言调用本程序时，前几个整数参数或返回值错位。

原理
当前 ABI 把前六个整数参数放进规定的寄存器，返回值放进返回值寄存器。x86-64 使用 rdi、rsi、rdx、rcx、r8、r9 与 rax。AArch64 使用 x0 至 x5 与 x0。本节调用汇编函数 abi_sum6，六个参数之和为 21。

证明
abi_sum6(1, 2, 3, 4, 5, 6) 的返回值是 21。六个参数与返回值寄存器的对应关系留在反汇编中。

=== CPU-005
应用
基类指针调用成员函数，实际执行了基类实现，派生类的覆盖没有生效。

原理
虚函数调用按对象的动态类型选择覆盖函数。Base* 指向 Derived 对象时，value() 返回 7。虚表槽位和间接调用指令留在反汇编中。

证明
Base* 指向 Derived 对象，value() 返回 7，调用的是派生类覆盖函数。

=== CPU-006
应用
文件无法作为可执行文件打开，或加载器报告架构不匹配。

原理
ELF 文件头的前四个字节是 0x7f、E、L、F。第 5 个字节为 2 表示 ELF64。这是 System V ABI 的文件格式。

证明
本进程可执行文件的前四个字节是 7f、E、L、F，类别字节为 2，与图中的 ELF64 标识一致。

=== CPU-007
应用
进程入口不是 main，动态库没有被装入，或程序在进入用户代码之前退出。

原理
程序头中的 PT_INTERP 给出动态加载器路径。内核先启动该加载器，再由加载器进入程序。没有这一项时，本节记为当前主机不能完成这项观察。

证明
程序头中存在类型为 PT_INTERP 的项。动态加载器先于 main 启动。

=== CPU-009
应用
计数偶发少一段，怀疑并发的加减被拆成了读、改、写。

原理
同一线程上，atomic 的 store 与 fetch_add 按程序顺序可见。本节先写入 1，再写入 2，再加 3。fetch_add 返回的旧值是 2，最终值是 5。具体指令是 lock、xchg 还是 dmb，由反汇编记录。

证明
先存入 2，再加 3。fetch_add 返回 2，最终值为 5。读改写的数值在本线程上保持连续。

=== CPU-010
应用
含分支的循环变慢，需要确认两边的计算结果仍然正确。

原理
语言只规定两种循环各自算出确定的校验和。单次耗时是一个样本，不作为哪种分支模式更快的判定。

证明
固定走向的循环和混合走向的循环都得到非 0 校验和。耗时只作为一次样本记录。

# 编译器可以改写的部分
优化之后，调试器中的变量、源码里的分支和对象的内存布局会与未优化构建不同。下面各节先固定语言要求的结果，再把指令是否被改写留给反汇编对照。

=== CPU-003
应用
打开优化之后，调试器里看不到某个局部变量，或者该变量的地址上不再有写入。

原理
没有被取地址的值可以由编译器放进寄存器。被取地址的局部变量必须能从内存读回写入的值。本节把 volatile int 设为 7 并取地址，读回结果为 7。Debug 与 Release 的栈帧差异由两次构建的反汇编对照。

证明
被取地址的局部变量读回 7。优化可以改写没有被取地址的值，不能改掉这个读回结果。

=== CPU-008
应用
优化前后返回值相同，但怀疑编译器改写了源码中的乘法和不会执行的分支。

原理
抽象机把 constant_result 求值为 6。常量折叠和删除不可达分支是编译器允许的改写，是否发生只出现在反汇编对照里。

证明
constant_result() 的返回值是 6。未优化和优化两次构建都保持这个抽象机结果。

=== RT-001
应用
把结构体按字节写入文件或网络后，对端字段错位；或者把含虚函数的对象当成普通内存块复制。

原理
标准布局类型 Sample 的首字段偏移为 0。含虚函数的 Base 是多态类型，id() 返回 1。非标准布局的字段偏移和虚表位置不是语言保证。

证明
Sample::first 的偏移为 0。Base 是多态类型，id() 返回 1。

=== RT-002
应用
catch 接到了异常对象，但类型判断把派生类当成了基类本身。

原理
catch (const Base&) 可以捕获 Derived。处理函数参数的静态类型是 Base，typeid(object) 给出动态类型 Derived。异常表和 typeinfo 的符号布局属于 ABI，本节不比对符号名。

证明
catch (const Base&) 捕获 Derived，typeid 与 Derived 相等。静态类型和动态类型因此分开。

# 分配与地址空间
分配失败、释放后读到旧数据、统计不归零和段错误，先表现为业务缓冲或对象寿命异常。下面各节分别核对线性分配、固定块、空闲合并、伙伴系统、大小类、线程缓存、映射、保护位和所有权。

=== MEM-001
应用
请求缓冲按顺序划出。释放中间一块之后，后续分配拿到了已释放区间里的旧数据，或同一块被释放两次。

原理
这个线性分配器只从尾部按后进先出退回。释放最后一块之后，下一次相同请求返回同一地址。再次释放同一块抛出 syslab::Error。中间的空洞不重新分配。它不替换全局 new。

证明
释放最后一次 32 字节分配后，下一次相同请求返回同一地址。第二次释放同一块抛出错误。

=== MEM-002
应用
固定大小的对象池在对象数量达到上限后继续分配成功，或把大于块大小的请求放进池里。

原理
池中有 4 个 32 字节块。第 5 次 32 字节请求返回空指针。64 字节请求返回空指针。归还一块之后，下一次 32 字节请求成功。

证明
4 个 32 字节块分配成功。第 5 次和 64 字节请求都失败。归还一块后，32 字节请求再次成功。

=== MEM-003
应用
已释放的总字节数足够，但一次较大的分配仍然失败。

原理
空闲链表把相邻空闲区间合并。三块 1000 字节全部释放后，一次 2500 字节的请求能够成功。不相邻的空闲区间不会被当成一整块。

证明
三块相邻的 1000 字节释放之后，2500 字节的请求分配成功。

=== MEM-004
应用
伙伴分配器上同时存活的几块缓冲互相覆盖。

原理
这个实现按 2 的幂切分。八次 24 字节分配各自写入不同的字节模式，读回必须与写入一致。全部释放后，一次 128 字节分配能够成功。映射大小保持为请求的 2 的幂。

证明
八块同时存活的 24 字节区域读回各自写入的字节。全部释放后，128 字节请求分配成功。

=== MEM-005
应用
小对象和大对象释放之后，分配器统计仍然显示有字节未归还。

原理
不超过大小类的请求进入大小类。超过最大类的请求使用单独映射。两条路径都释放后，allocated_bytes 为 0。

证明
24 字节请求和 8192 字节请求都释放之后，已分配字节为 0。

=== MEM-006
应用
一个线程释放的内存没有回到分配它的缓存，或者一个尺寸的空闲块被发给了另一个尺寸的请求。

原理
线程缓存的箱按精确请求大小存放。四个线程各自分配并释放 40 个 32 字节块之后，统计中的 allocated_bytes 为 0。缓存中的 20 字节块不会返回给 32 字节请求。

证明
四个线程分配并释放 32 字节块之后，已分配字节为 0。

=== MEM-007
应用
mmap 之后读回的字节与写入不一致。

原理
匿名私有映射上，写入 128 个字节 0x5a，同一映射的最后一个字节读回 0x5a。本节不判断这些页是否已经驻留物理内存。

证明
映射写入 0x5a 之后，同一映射的第 128 个字节读回 0x5a。

=== MEM-008
应用
段错误出现后，无法判断是哪一个进程改了保护位，以及信号落在哪一个进程。

原理
子进程把映射改为 PROT_NONE 并写入。内核向该子进程投递 SIGSEGV。父进程继续存活，并观察到子进程因 SIGSEGV 终止。

证明
子进程在 PROT_NONE 的页上写入后因 SIGSEGV 终止。父进程仍在运行并读到该终止状态。

=== MEM-009
应用
对象在仍被使用时析构，或者最后一个使用者离开后对象仍然没有析构。

原理
unique 转移后，原指针为空，新指针持有对象。shared 离开作用域后，两个节点都析构。weak 不延长寿命，作用域结束后 expired 为真。

证明
作用域结束时两个节点都析构，weak 已经过期。unique 转移后原指针为空，新指针中的值是 4。

=== MEM-010
应用
分配器在空请求、空指针释放或同一块的第二次释放上崩溃，或者统计因此漂移。

原理
0 字节请求抛出错误。空指针释放是空操作。同一块的第二次释放抛出错误。

证明
0 字节请求抛出错误。空指针释放没有抛出。同一块的第二次释放抛出错误。

# 进程、线程和内核可见的事实
日志串线、数据串到错误的执行流、通知丢失和延迟解释，先出现在业务观测里。下面各节核对系统调用、fork 之后的写入、tid、地址空间、条件谓词、亲和性、切换计数、进程间数据、信号处理和 NUMA 节点数量。

=== OS-001
应用
日志或性能分析认为某次调用多进了一次内核，但名单与跟踪对不上。

原理
getpid 返回当前进程的正数标识。系统调用跟踪记录本次实际出现的入口。跟踪工具不存在时，观察记为不可用，返回值检查仍然有效。

证明
getpid 返回正数。跟踪里实际出现的调用以本次记录为准。

=== OS-002
应用
fork 之后，父进程或子进程看到了对方后来写入的变量。

原理
子进程在 fork 之后把变量改为 2 并退出。父进程中的同一变量保持为 1。地址空间分离解释这次隔离。缺页次数不能单独证明写时复制。

证明
子进程把变量写成 2 并正常退出。父进程中的同一变量仍是 fork 之前的 1。

=== OS-003
应用
多线程日志混在一起，无法判断一行来自哪个执行流。

原理
Linux 为每个任务分配不同的 tid。父线程与新线程的 tid 都为正数，并且互不相等。本节不描述 task_struct 的布局。

证明
父线程与新线程的 tid 都为正数，并且互不相等。

=== OS-004
应用
一次写入只在一部分执行流里可见，需要判断那些执行流是线程还是进程。

原理
同一进程的线程共享地址空间，新线程写入的 1 在 join 之后对原线程可见。fork 出的子进程写入 5，不改变父进程中的 1。

证明
新线程写入的 1 在 join 之后可见。子进程写入的 5 不改变父进程中的值。

=== OS-005
应用
条件变量上的等待者被唤醒后继续使用旧数据，或者通知发出时等待者尚未进入等待。

原理
等待者在持锁状态下反复检查谓词 value == 7。通知方在持锁时把 value 设为 7 再通知。等待者返回时谓词已经成立。伪唤醒由谓词复查挡住。本节不证明 futex 进入了睡眠。

证明
等待线程返回时，持锁发布的 value 已经是 7。

=== OS-006
应用
线程没有运行在指定的 CPU 上。

原理
sched_setaffinity 把掩码设为只含 CPU 0 之后，sched_getaffinity 读回的掩码包含 CPU 0。调度器仍可能推迟该线程实际上 CPU。设置失败时，本节记为当前主机不能完成这项观察。

证明
读回的亲和性掩码包含 CPU 0。

=== OS-007
应用
用自愿上下文切换次数解释一次 yield 带来的延迟。

原理
连续 1000 次 sched_yield 前后，ru_nvcsw 的差值是内核报告的自愿切换样本。差值为 0 仍然是有效样本，不能据此判定切换没有发生或一定发生。

证明
1000 次 sched_yield 前后的 ru_nvcsw 差值已经记录。差值为 0 也是一次有效样本。

=== OS-008
应用
进程之间的数据没有到达，需要区分字节流和共享内存。

原理
管道写入两个字节 ok 后，读端得到同样的字节。MAP_SHARED 匿名映射上，子进程写入 42，父进程读到 42。

证明
管道读回写入的两个字节。MAP_SHARED 映射上，父进程读到子进程写入的 42。

=== OS-009
应用
已经调用 raise 或 kill，处理函数没有执行。

原理
sigaction 安装 SIGUSR1 的处理函数后，raise 使该函数执行一次，delivered 变为 1。处理函数仍然受异步信号安全约束。

证明
SIGUSR1 的处理函数执行了一次，delivered 为 1。

=== OS-010
应用
准备比较跨 NUMA 节点的内存延迟。

原理
sysfs 中可见的节点目录少于两个时，主机不能做跨节点比较，结果为不支持。节点不少于两个时，本节只记录节点数量，不绑定内存，也不比较延迟。

证明
可见 NUMA 节点不少于两个。本次只记录节点数，不比较延迟。

# 锁
临界区里的计数偏小、同一线程再次加锁后死锁、许可超卖，都是业务计数或资源数量先出错。下面各节核对测试并设置、票据、MCS、futex 互斥量、读写锁、递归、条件谓词、信号量、屏障和只执行一次。

=== SYNC-001
应用
自旋锁保护的计数小于线程数乘以每次循环的递增次数。

原理
四个线程在同一把测试并设置锁内各递增 2000 次。临界区结束时计数为 8000。这把锁不保证先到先服务。

证明
四个线程在测试并设置锁内各递增 2000 次，计数为 8000。

=== SYNC-002
应用
票据锁保护的计数偏小，或线程进入临界区的顺序与取号顺序不符。

原理
取号和服务号是同一把锁上的一对计数。四个线程各递增 2000 次后，计数为 8000。这个实现按票号交接。

证明
四个线程在票据锁内各递增 2000 次，计数为 8000。

=== SYNC-003
应用
MCS 锁在解锁时崩溃，或临界区计数偏小。

原理
每个等待者使用自己的队列节点，节点的寿命必须覆盖到 unlock 返回。McsGuard 把节点放在守卫内部。四个线程各递增 1000 次后，计数为 4000。

证明
四个线程各持有 MCS 锁递增 1000 次，计数为 4000。队列节点的寿命覆盖到 unlock 返回。

=== SYNC-004
应用
互斥量保护的计数偏小，或等待行为与锁的状态对不上。

原理
这把 futex 互斥量区分未锁、已锁无人等待、已锁且有等待者。四个线程各递增 2000 次后，计数为 8000。慢路径是否进入睡眠由 SYNC-010 单独计数。

证明
四个线程在 futex 互斥量内各递增 2000 次，计数为 8000。

=== SYNC-005
应用
读写锁下写者的计数被共享持有者打断，或共享路径无法完成。

原理
写者持有互斥的写锁并递增 100 次，结果为 100。三个线程的共享锁路径能够完成。写优先是这个实现的策略。POSIX 读写锁还有其他合法策略。

证明
写锁互斥下的递增结果为 100。共享锁路径已经完成。

=== SYNC-006
应用
同一线程再次加锁后死锁，或者其他线程在持有者重入期间进入了临界区。

原理
拥有者线程可以连续 lock 两次，再 unlock 两次。其他线程之间仍然互斥。四线程计数为 2000。非拥有者不能借用递归计数进入临界区。

证明
同一线程连续加锁两次并解锁两次。随后四线程在递归互斥量内的计数为 2000。

=== SYNC-007
应用
等到了互斥量，读到的仍是通知之前的旧值。

原理
谓词 value == 7 在持锁期间发布，等待者在持锁期间复查。等待线程返回时 value 为 7。允许伪唤醒。本节不证明 futex 一定睡眠。

证明
等待线程返回时，持锁发布的谓词 value 为 7。

=== SYNC-008
应用
同时使用某项资源的线程数超过了设定的许可数。

原理
信号量初值为 2。四个线程反复获取许可，观测到的最大并发不超过 2。调度没有让两个持有者重叠时，最大并发小于 2 仍然通过。超过 2 才是失败。

证明
同时持有的许可数不超过初值 2。

=== SYNC-009
应用
屏障返回之后，仍有线程看到尚未到达的参与者。

原理
四个参与者都到达后，每个线程看到的到达计数为 4。到达计数用原子发布。等待的是代数。

证明
屏障返回后，每个参与者看到的到达计数都是 4。

=== SYNC-010
应用
初始化函数执行了多次，或者把慢路径计数当成线程已经在 futex 上睡眠。

原理
锁已被持有时，另一个线程进入 Mutex 的慢路径，slow_path_count 在解锁前大于 0。该计数在快速比较交换失败时增加，不证明 futex 已经睡眠。八个线程调用 OnceFlag，初始化函数只进入一次。

证明
锁已被持有时，slow_path_count 在解锁前大于 0。八个线程的初始化函数只进入一次。

# 原子操作与内存序
共享计数偶发偏差、旗标为真但载荷仍旧、两个读取同时看见 0，都先表现为业务数据不一致。下面各节从互斥保护开始，再分开原子性、release/acquire、seq_cst、栅栏、版本号、无锁容器和回收。

=== AT-001
应用
多个线程共同维护一个计数，业务上需要这个计数等于全部递增之和。

原理
四个线程在互斥量保护下各递增 1000 次，计数为 4000。未同步的普通整数递增是数据竞争。本节不运行那条路径，因此一次未崩溃不能证明不存在数据竞争。

证明
四线程在互斥量保护下各递增 1000 次，计数为 4000。

=== AT-002
应用
计数总和正确，但同一时刻发布的其他普通数据仍然是旧值。

原理
relaxed fetch_add 保证读改写的原子性。四线程共 40000 次之后计数为 40000。relaxed 不建立与其他内存的 happens-before。

证明
40000 次 relaxed fetch_add 之后，计数为 40000。这次总和只证明原子性。

=== AT-003
应用
旗标已经为真，读到的载荷仍是写入旗标之前的旧值。

原理
写线程用 relaxed 写入载荷 42，再用 release 写入旗标 1。读线程用 acquire 看到旗标为 1 之后，载荷为 42。重复 200 次。这是语言内存模型的要求。

证明
200 次试验中，acquire 看到旗标为 1 之后，载荷都是 42。

=== AT-004
应用
两个线程各自先写自己的变量再读对方的变量，两边都读到 0。

原理
seq_cst 不允许这次存储缓冲结果中两个加载同时为 0。300 次试验中不出现该结果。relaxed 或 acq_rel 允许该结果，本节不把那种允许的结果当成失败。

证明
300 次 seq_cst 试验中，没有出现两个加载同时为 0。

=== AT-005
应用
两个读者对两个写入的观察顺序互相交叉，业务上认为全局顺序被破坏。

原理
seq_cst 禁止 r1 为 1、r2 为 0、r3 为 1、r4 为 0 这一组结果。200 次没有出现，只说明这批样本没有违反约束。

证明
200 次样本中没有出现被 seq_cst 禁止的那组交叉结果。

=== AT-006
应用
已经使用 relaxed 原子和栅栏，旗标为真时载荷仍是旧值。

原理
写线程在 relaxed 存储载荷之后执行 release fence，再 relaxed 存储旗标。读线程看到旗标后执行 acquire fence，再读取载荷。重复 200 次，载荷为 42。这里核对的是 C++ 的 atomic_thread_fence。

证明
200 次试验中，acquire fence 之后读到的载荷都是 42。

=== AT-007
应用
无锁结构里，节点被释放后又分配到同一地址，比较交换把新节点误认成旧节点。

原理
本节用一个 64 位字的高 32 位做版本号。第一次比较交换把版本从 0 改为 1。随后仍用版本 0 的期望值做比较交换，必须失败，低 32 位保持为 1。这是版本号使旧期望失效的演示。

证明
版本号从 0 改为 1 之后，仍携带版本 0 的比较交换失败，字的低 32 位保持为 1。

=== AT-008
应用
两个线程分别递增相邻的计数器，耗时明显长于分开存放的计数器，计数本身是否完成尚未确认。

原理
相邻布局和按缓存行填充的布局都完成递增，两次之和都是 400000。耗时差取决于微架构，不作为通过条件。

证明
相邻布局和填充布局的递增之和都是 400000。耗时只作为样本记录。

=== AT-009
应用
无锁栈在并发压入之后丢失元素或弹出重复值。

原理
四个线程共压入 800 个互异值。弹出值的集合大小为 800。指针原子不是始终无锁时，结果为不支持。该栈不是 wait-free。

证明
弹出值的集合大小为 800，与压入的互异值数量相同。

=== AT-010
应用
单生产者单消费者队列交出的整数乱序或出现缺口。

原理
容量为 2 的幂。一个生产者拥有尾，一个消费者拥有头。消费者依次得到 0 到 9999。第二个生产者或第二个消费者不属于这个算法。

证明
消费者依次得到 0 到 9999。

=== AT-011
应用
多个生产者和多个消费者结束后，元素丢失或重复。

原理
四个生产者各发送 500 个互异值。消费者集合大小为 2000。队列有界。元素类型必须可平凡复制。索引原子不是始终无锁时，结果为不支持。

证明
消费者收到的互异值数量为 2000，与四个生产者发送的数量相同。

=== AT-012
应用
无锁结构在读者仍持有某个地址时回收了该地址，随后发生释放后使用。

原理
危险指针仍发布该地址时，回收跳过它。保护期间删除计数等于阈值减 1。清除槽后继续退役，最终删除计数等于两倍阈值再加上阈值减 1。阈值是本教学域的参数：每线程槽数乘以最大线程数。

证明
地址仍被危险指针发布时，该对象没有被删除。清除发布之后，后续扫描回收了它。

=== AT-013
应用
读者仍在使用对象时，回收逻辑已经删除该对象。

原理
线程处于 pin 期间退役一个对象，删除计数为 0。unpin 后再退役两个对象，删除计数为 2。最后一个对象可以留到下一次宽限期。

证明
pin 期间退役一个对象后，删除计数为 0。unpin 后再退役两个对象，删除计数为 2。

=== AT-014
应用
把这台机器上观察到的原子指令形式写成所有架构的结论。

原理
当前二进制只为一种 ISA 编译。x86-64 与 AArch64 的宏恰好一个成立。其他架构返回不支持。一次运行不能对照另一套指令集。

证明
当前二进制只命中一种 ISA 宏。这次运行不能推广到另一种指令集。

# 缓存访问
扫描变慢或带宽数字异常时，先要确认计算或复制的结果仍然正确。下面各节核对顺序访问与跨步访问的校验和、复制后的逐字节内容，以及两种布局的计数。

=== CACHE-001
应用
按固定跨步扫描数组比顺序扫描慢，需要先确认两边算出的校验和都正确。

原理
顺序访问和跨步 16 的访问都得到非 0 校验和。一次耗时是样本。谁更快不作为通过条件。CPU 型号记在环境快照里。

证明
顺序访问和跨步访问的校验和都不为 0。耗时只作为一次样本记录。

=== CACHE-002
应用
复制带宽的数字异常，目的缓冲区的内容尚未与源缓冲区核对。

原理
memcpy 复制 8 MiB 之后，目的缓冲区与源缓冲区逐字节相同。单次耗时不是带宽中位数，也没有绑定频率或 NUMA 节点。

证明
8 MiB 复制之后，目的缓冲区与源缓冲区逐字节相同。耗时只作为一次样本记录。

=== CACHE-003
应用
两个计数器放在相邻地址时变慢，需要先确认两种布局都完成了递增。

原理
相邻数组元素和分开对齐的两个原子，计数和都是 200000。相邻元素是否落在同一缓存行取决于 ABI 布局。耗时差异不是通过条件。

证明
相邻布局和分开布局的计数和都是 200000。

# 协程和 fiber
任务卡住、异常没有回到调用方、并行求和与公式不符，先出现在业务输出里。下面各节核对 fiber 的让出、协程挂起点，以及工作窃取的总和。

=== CO-001
应用
协作式任务卡住，后续任务没有机会运行。

原理
两个 fiber 在 yield 处交替，日志为 A1B1A2B2。不调用 yield 的 fiber 不会被抢占。这是 ucontext 切换，不是内核线程。

证明
两个 fiber 在 yield 处交替，日志为 A1B1A2B2。

=== CO-002
应用
协程中的异常没有到达调用 run 的一方，或者两个任务的输出顺序与挂起点不符。

原理
两个协程在挂起点交替，日志为 ACBD。任务抛出 runtime_error 时，run 重新抛出该异常。协程在调度器恢复之前不运行，也不自动并行。

证明
两个协程在挂起点交替，日志为 ACBD。run 重新抛出任务中的 runtime_error。

=== CO-003
应用
并行求和的结果与串行公式不一致。

原理
工作窃取把 0 到 999 分给工作者，总和等于 999 * 1000 / 2。每个工作者使用自己的双端队列。被窃取的下标仍然来自这个区间。

证明
0 到 999 的并行求和等于 999 * 1000 / 2。
