# 复制与移动
复制含指针的对象时，复制的可以是指针，也可以是指针所指的内容。移动则把资源转给新对象。这两节分别核对复制和移动。

=== OBJ-001
名词
浅拷贝复制指针。深拷贝另分配内存并复制值。

重点
浅拷贝和深拷贝改的是不是同一块内存？

背景
在 C++ 对象模型中，复制一个对象是按成员生成另一份成员。函数按值传递，或再用复制构造保存时，都会走这条路径。成员若是指针，被复制的是地址，新对象与源对象指向同一块存储。此后改这块存储，两个对象读到的是同一次写入。

另行分配一块存储，并把复制当时的值写进去，两块存储才各自独立。后来的修改只出现在被写的那一块。这是调用方额外写出的操作。标准没有把它定义成一个叫“深拷贝”的关键字。

语言
C++ 的默认复制按成员进行。复制指针成员得到的是地址，两份指针指向同一对象。另分配存储并复制值是额外写出的操作，标准里没有一个叫“深拷贝”的关键字。

机制
浅拷贝复制的是地址。两个指针指向同一对象时，对其中一个指针的写入会被另一个指针的读取观察到。深拷贝复制的是当时的值，新存储和旧存储上的写入互不覆盖。本课用裸指针作出这两种复制，不定义类的拷贝构造函数，也不执行移动。

程序
程序让浅拷贝与源指针地址相同，把源值改为 9 后读取浅拷贝。再分配另一块内存作为深拷贝，把源值改为 9 后读取深拷贝。

证明
浅拷贝与源对象是同一地址。源对象改为 9 后，浅拷贝也是 9。
深拷贝是另一地址。源对象改为 9 后，深拷贝仍是 7。

=== OBJ-002
名词
移动构造把资源交给新对象，并把源对象留在可以析构的空状态。

重点
移动构造之后，值和指针分别在哪个对象里？

背景
在 C++ 的对象生命周期里，析构函数释放对象仍然持有的资源。堆内存和文件描述符通常只能有一个释放者。把同一个指针复制给两个对象后，两个析构都会释放它。

把资源交到新对象、源对象不再持有，称为移动。移动之后，源对象必须仍能安全析构，标准称这种状态为有效但未指定。本课的 Holder 把源指针置空。置空只是它选择的一种有效状态，不是标准对每种类型的要求。

语言
移动之后，源对象必须处于有效但未指定的状态。本课的 Holder 把指针置空，这是一种有效状态，不是标准对每一种类型的要求。本节删除了拷贝构造。

机制
Holder 的移动构造复制指针，然后把源对象的指针置空。析构只删除自己仍持有的指针。

程序
程序构造持有 4 的源对象，用移动构造产生新对象，再检查源指针和新对象中的值。

证明
移动构造之后，源对象的指针为空。
新对象持有原来的地址，值仍是 4。

# 数、调用和可执行文件
数值的字节、函数返回值、参数寄存器、虚函数选择、ELF 标识和动态加载器，决定的是不同的结果。各节只核对其中一项。

=== CPU-001
名词
整数按补码存放。IEC 559 的 1.0f 是一种固定的 binary32 位型。

重点
int 的 -1 在内存里是什么字节？IEC 559 的 1.0f 是什么位型？

背景
进程的内存里，整数和浮点数都按字节存放。调试器、转储和二进制协议读到的是这些字节，不是源码里的 -1 或 1.0。带符号整数的编码叫补码：-1 的每一位都是 1，所以每个字节都是 0xff，从哪一端读都一样。字节序只改变多字节整数里各字节的位置。

浮点数用另一套编码。C++ 用 numeric_limits<float>::is_iec559 声明 float 是否符合 IEC 559。为真时，1.0f 才能拆成符号、偏置阶码和尾数。没有这项声明时，不能按这套字段解释读到的 32 位。

语言
C++20 [basic.fundamental] 要求带符号整数使用补码。因此 int 的 -1 在值表示里是全 1，每个字节都是 0xff。numeric_limits<float>::is_iec559 为真时，float 符合 IEC 559，1.0f 的 binary32 才是符号 0、偏置阶码 127、尾数 0。

机制
补码把 -1 表示成全 1，所以 int 的每个字节都是 0xff，与字节序无关。IEC 559 binary32 把 1.0 编成偏置阶码 127 和零尾数，符号位为 0。本课只在实现报告 is_iec559 时核对这 32 位。页面上的填数观察按小端序从低地址列出任意 int32 和 float32，用来对照同一条规则；本机执行仍只核对 -1 和 1.0f。

程序
程序逐字节读取 int 的 -1，并在 is_iec559 为真时读取 1.0f 的 32 位。

证明
int -1 的每个字节都是 ff，与图中的四个字节一致。
numeric_limits<float>::is_iec559 为真，继续读取 1.0f 的内存。
1.0f 的符号、阶码和尾数与图中的 binary32 布局一致。

=== CPU-002
名词
函数返回值由语言规定。参数落在哪个寄存器由调用约定规定。

重点
一次普通调用的返回值由谁规定？

背景
函数调用分两层。语言规定参数算完之后返回值等于什么。机器再规定这个返回值从哪个寄存器交回、参数从哪些寄存器进入。后者叫过程调用标准，不是抽象机的一部分。

写出 add_six(1, 2, 3, 4, 5, 6) 时，语言规定的结果是六个数之和。和数对不上，先查这个返回值。程序在返回之后崩溃，再查寄存器。寄存器留在下一节。

语言
抽象机规定 add_six(1, 2, 3, 4, 5, 6) 的返回值是 21。参数进入哪个寄存器由调用约定规定，在下一节对照反汇编。这一节的通过条件只有返回值。

机制
语言要求 add_six(1, 2, 3, 4, 5, 6) 的返回值等于 21。参数进入哪个寄存器属于调用约定，由反汇编观察，不作为本节的数值条件。

程序
程序调用 add_six(1, 2, 3, 4, 5, 6)，只比较返回值是否为 21。

证明
add_six(1, 2, 3, 4, 5, 6) 的返回值是 21，与图中的返回值一致。

=== CPU-004
名词
本机 ABI 把前六个整数参数和返回值放在固定的寄存器里。

重点
前六个整数参数和返回值落在哪些寄存器？

背景
过程调用标准规定整数参数和返回值使用哪些寄存器。汇编和另一种语言不读 C++ 的参数列表，只按这个标准放置整数。

在 x86-64 上，这个标准是 System V AMD64 ABI：前六个整数依次进入 rdi、rsi、rdx、rcx、r8、r9，结果从 rax 取出。在 AArch64 上，前六个整数进入 x0 至 x5，结果从 x0 取出。寄存器放错，被调函数读到的就不是准备好的参数。本节的通过条件仍是返回值 21。

语言
本机遵循 System V AMD64 ABI。INTEGER 类参数依次使用 rdi、rsi、rdx、rcx、r8、r9，整数返回值使用 rax。AArch64 的前六个整数参数使用 x0 到 x5，返回值使用 x0。本节的通过条件是返回值 21；寄存器只在反汇编里看。

机制
当前 ABI 把前六个整数参数放进规定的寄存器，返回值放进返回值寄存器。x86-64 使用 rdi、rsi、rdx、rcx、r8、r9 与 rax。AArch64 使用 x0 至 x5 与 x0。本节调用汇编函数 abi_sum6，六个参数之和为 21。

程序
程序调用汇编函数 abi_sum6，用返回值 21 闭合这六个参数。

证明
abi_sum6(1, 2, 3, 4, 5, 6) 的返回值是 21。六个参数与返回值寄存器的对应关系留在反汇编中。

=== CPU-005
重点
基类指针调用虚函数时，执行哪一个函数？

背景
通过基类指针调用函数时，编译期看到的类型和运行时对象的类型可以不同。前者叫静态类型，只决定能写哪些调用。后者叫动态类型，虚函数按它选择实际执行的版本。

指针的静态类型是基类、动态类型是派生类时，执行的是派生类的覆盖。选错版本时，到对象和它的函数表里查。函数表的槽位留在反汇编中。

语言
虚函数调用选择对象的动态类型所覆盖的函数。

机制
虚函数调用按对象的动态类型选择覆盖函数。Base* 指向 Derived 对象时，value() 返回 7。虚表槽位和间接调用指令留在反汇编中。

程序
程序用 Base* 指向 Derived，调用 value()，期望结果为 7。

证明
Base* 指向 Derived 对象，value() 返回 7，调用的是派生类覆盖函数。

=== CPU-006
重点
一个文件怎样被识别为 ELF64？

背景
内核装入程序之前，先识别文件格式。ELF 把标识放在文件最前面的一段，这段叫 e_ident。前四字节必须是 0x7f、E、L、F，否则不把文件当成 ELF。

第 5 字节表示位数。它等于 2 时，文件是 64 位 ELF，标准里的名字是 ELFCLASS64。这个字节和当前程序不符，加载器报告架构不匹配，控制进不了 main。

语言
gABI 规定 e_ident 的前四字节是 0x7f、E、L、F，第 5 字节 EI_CLASS 为 2 表示 ELFCLASS64。这是文件格式，不是 C++ 语言规则。

机制
ELF 文件头的前四个字节是 0x7f、E、L、F。第 5 个字节为 2 表示 ELF64。这是 System V ABI 的文件格式。

程序
程序读取本进程可执行文件的前 16 字节，核对魔数和类别字节。

证明
本进程可执行文件的前四个字节是 7f、E、L、F，类别字节为 2，与图中的 ELF64 标识一致。

=== CPU-007
重点
main 之前由谁启动动态链接的程序？

背景
动态链接的程序在进入 main 之前，要先装入依赖库。内核从程序头里找解释器路径。这个程序头项的类型叫 PT_INTERP，路径指向动态加载器。

内核先启动加载器。加载器完成装入和重定位，再进入程序入口。没有这一项，内核没有解释器可启动。入口停在加载器或库没有出现，先看程序头里有没有它。

语言
PT_INTERP 是程序头中的一项，内核据此启动动态加载器。

机制
程序头中的 PT_INTERP 给出动态加载器路径。内核先启动该加载器，再由加载器进入程序。没有这一项时，本节记为当前主机不能完成这项观察。

程序
程序扫描本进程 ELF 的程序头，确认存在类型为 PT_INTERP 的项。

证明
程序头中存在类型为 PT_INTERP 的项。动态加载器先于 main 启动。

=== CPU-009
重点
同一线程上的原子读改写，数值是否连续？

背景
多个线程改同一个计数时，普通的加一是三次内存访问：读出、修改、写回。另一线程夹在中间，两次可能读到同一个旧值，后一次写回盖掉前一次，计数就少一段。

把这三步合成一次、中间不能插入其他线程的操作，称为原子读改写。同一线程按程序顺序再读，看到的是这次修改之后的值。机器用哪条指令完成它，不改变旧值和最终值的先后。

语言
原子对象上的修改对本线程按程序顺序可见。指令形式属于 ISA，留在反汇编中。

机制
同一线程上，atomic 的 store 与 fetch_add 按程序顺序可见。本节先写入 1，再写入 2，再加 3。fetch_add 返回的旧值是 2，最终值是 5。具体指令是 lock、xchg 还是 dmb，由反汇编记录。

程序
程序依次存入 1、存入 2、再加上 3，核对旧值和最终值。

证明
先存入 2，再加 3。fetch_add 返回 2，最终值为 5。读改写的数值在本线程上保持连续。

=== CPU-010
重点
两种分支循环变慢时，计算结果是否仍然成立？

背景
循环里的分支先判断条件，条件成立才把值加进结果。处理器会猜测分支方向。猜错时，已经开始的那条路径被丢掉，这一次循环更慢。语言上的总和仍是条件为真的那些值。

走向固定的循环和随数据变化的循环可以生成不同指令。两边的校验和各自由自己的条件决定。一次耗时是样本，不能单独证明哪种分支模式更快。

语言
语言规定的是校验和。分支预测器的行为不是语言规则。

机制
固定走向的条件对这组数据恒为真，校验和等于 20 次 0 到 199999 的和。混合走向按 (value * 17) & 64 是否非 0 累加。只要求非 0 会放过少加元素的错误。单次耗时是一个样本，不作为哪种分支模式更快的判定。

程序
程序分别计算两种校验和，并与上面的和比较，再记录一次耗时。

证明
固定走向的校验和等于 20 次全元素之和。混合走向的校验和等于按条件累加的和。耗时只作为一次样本记录。

# 编译器可以改写的部分
编译器可以改指令和栈上的位置。语言规定的结果，以及被取地址对象的读回值，保持不变。各节先固定这个结果，指令差异留在反汇编里。

=== CPU-003
重点
优化之后，被取地址的局部变量还在不在内存里？

背景
编译器生成函数代码时，可以让一个局部值只存在于寄存器中。打开优化之后，调试器在栈上看不到它的写入。这种改写要保持程序能观察到的结果不变，标准把这条原则称为 as-if。

程序一旦取出这个对象的地址，它就必须留在内存里，从该地址能读回刚写入的值。优化可以改栈的样子，不能让这次读回消失。

语言
没有被取地址的值可以只存在于寄存器。被取地址的对象必须能从该地址读回。

机制
没有被取地址的值可以由编译器放进寄存器。被取地址的局部变量必须能从内存读回写入的值。本节把 volatile int 设为 7 并取地址，读回结果为 7。Debug 与 Release 的栈帧差异由两次构建的反汇编对照。

程序
程序把 volatile int 设为 7 并取地址，再从该地址读回。

证明
被取地址的局部变量读回 7。优化可以改写没有被取地址的值，不能改掉这个读回结果。

=== CPU-008
重点
优化可以改写乘法和死分支，返回值能否改变？

背景
函数在语言里的结果先确定。编译器可以事先算好乘法，也可以删掉永远走不到的分支，只要外面看到的结果不变。这条原则称为 as-if，写在 [intro.abstract]。

源码里的乘法和走不到的分支从反汇编里消失，是编译器做了这些改写。返回值变了，才是改写出了界。未优化和优化两次构建都核对同一个返回值。

语言
[intro.abstract] 的 as-if 规则允许编译器改写，只要可观察行为与抽象机一致。这个函数的抽象机结果是 6。常量折叠和删除不可达代码可以出现在反汇编里，不能改变这个返回值。

机制
抽象机把 constant_result 求值为 6。常量折叠和删除不可达分支是编译器允许的改写，是否发生只出现在反汇编对照里。

程序
程序调用 constant_result()，未优化和优化两次都核对返回值 6。

证明
constant_result() 的返回值是 6。未优化和优化两次构建都保持这个抽象机结果。

=== RT-001
重点
结构体按字节写出时，首字段在哪里？含虚函数的类型能不能当普通内存复制？

背景
结构体按字节写出时，接收方从对象起始地址加上字段偏移来读。字段在对象里的摆放称为布局。标准布局类型把第一个数据成员放在偏移 0，接收方可以从对象地址直接读到它。

带虚函数的类型要在运行时选择函数，这种类型称为多态类型，对象里带有实现用来分派的信息。把它当成同样长度的普通字节块复制后再当原类型使用，分派信息对不上。非标准布局的偏移和虚表位置不在语言保证之内。

语言
标准布局类型的首字段偏移为 0。含虚函数的类型是多态类型。

机制
标准布局类型 Sample 的首字段偏移为 0。含虚函数的 Base 是多态类型，id() 返回 1。非标准布局的字段偏移和虚表位置不是语言保证。

程序
程序检查 Sample::first 的偏移，并调用 Base::id()。

证明
Sample::first 的偏移为 0。Base 是多态类型，id() 返回 1。

=== RT-002
重点
catch 到基类引用时，对象的动态类型是什么？

背景
异常有两个类型。抛出时确定的是对象实际的类型，称为动态类型。catch 参数写成的类型是静态类型。用基类引用可以接住派生类对象，因为派生类对象也是基类对象。

进入处理代码之后，参数的静态类型仍是基类，对象的动态类型仍是当初抛出的派生类。typeid 报告动态类型。只用静态类型判断“这就是基类本身”，会把派生对象漏掉。异常表的符号布局属于调用约定，本节不比对符号名。

语言
处理函数参数的静态类型可以是基类，typeid 给出动态类型。

机制
catch (const Base&) 可以捕获 Derived。处理函数参数的静态类型是 Base，typeid(object) 给出动态类型 Derived。异常表和 typeinfo 的符号布局属于 ABI，本节不比对符号名。

程序
程序抛出 Derived，用 catch (const Base&) 捕获，再比较 typeid。

证明
catch (const Base&) 捕获 Derived，typeid 与 Derived 相等。静态类型和动态类型因此分开。

# 分配与地址空间
不同分配器按不同规则划出和收回内存。映射、页保护和对象所有权各自独立，不与分配器的空闲规则混在一节里。

=== MEM-001
重点
线性分配器释放一块之后，下一次分配会拿到哪一块？

背景
堆分配器负责划出和收回内存。线性分配器按地址往前划，释放只从尾部退回，适合一批临时对象一起结束的场合。退回最后一块之后，下一次相同大小的请求又得到这段地址。

释放中间的一块会留下空洞。这个分配器不把空洞交给后面的请求。若立刻交出去，仍拿着旧指针的调用方会看到新的写入。同一块再释放一次，是重复释放。它不替换全局 new。

语言
这个分配器只按后进先出退回尾部，中间空洞不重新分配。

机制
这个线性分配器只从尾部按后进先出退回。释放最后一块之后，下一次相同请求返回同一地址。再次释放同一块抛出 syslab::Error。中间的空洞不重新分配。它不替换全局 new。

程序
程序释放最后一次 32 字节分配，再分配同样大小，并第二次释放同一块。

证明
释放最后一次 32 字节分配后，下一次相同请求返回同一地址。第二次释放同一块抛出错误。

=== MEM-002
重点
固定块池什么时候拒绝请求？

背景
对象池在创建时定下每块多大、一共多少块，用来放同样大小的对象。请求比一块还大，池里没有放得下的块，分配失败，返回空指针。

空闲块用完之后，后来的请求同样失败，池不向外扩大。把过大的请求写进一块里，写入会越过这块的结尾。这个上限是池自己的参数，不是 malloc 的通用合同。

语言
池的容量和块大小是这个分配器的参数，超出任一条都返回空指针。

机制
池中有 4 个 32 字节块。第 5 次 32 字节请求返回空指针。64 字节请求返回空指针。归还一块之后，下一次 32 字节请求成功。

程序
程序分配 4 个 32 字节块，再请求第 5 个和 1 个 64 字节，然后归还一块再分配。

证明
4 个 32 字节块分配成功。第 5 次和 64 字节请求都失败。归还一块后，32 字节请求再次成功。

=== MEM-003
重点
空闲字节够用，为什么一次较大的分配仍然失败？

背景
空闲链表把空出来的区间记下来，供以后的请求使用。只有地址相邻的空闲区间能合成一整段。已经释放的字节加起来够，并不表示有一段连续空间能满足下一次请求。

中间还夹着正在使用的块时，两边的空闲字节拼不到一起，较大的请求失败。三块相邻区间都释放之后，较大的请求才能从合成后的区间里划出。

语言
只有相邻空闲区间能合并成一次请求。不相邻的空闲字节不能拼成一块。

机制
空闲链表把相邻空闲区间合并。三块 1000 字节全部释放后，一次 2500 字节的请求能够成功。不相邻的空闲区间不会被当成一整块。

程序
程序释放三块相邻的 1000 字节，再请求 2500 字节。

证明
三块相邻的 1000 字节释放之后，2500 字节的请求分配成功。

=== MEM-004
重点
按 2 的幂切开的块，会不会互相覆盖？

背景
伙伴分配把地址区间切成大小为 2 的幂的块。同时还活着的对象必须落在不同的块上，写入才不会叠在一起。

两块都空了，并且正好互为伙伴，才合并成上一层更大的块。把还在使用的块和它的伙伴合并，下一次分配会把这块再交出去。

语言
伙伴分配把区间切成 2 的幂。同时存活的块必须落在不同区间。

机制
这个实现按 2 的幂切分。八次 24 字节分配各自写入不同的字节模式，读回必须与写入一致。全部释放后，一次 128 字节分配能够成功。映射大小保持为请求的 2 的幂。

程序
程序同时持有八块 24 字节，各自写入并读回，全部释放后再请求 128 字节。

证明
八块同时存活的 24 字节区域读回各自写入的字节。全部释放后，128 字节请求分配成功。

=== MEM-005
重点
小请求和大请求释放后，统计为什么对不上？

背景
分配器常把小请求和大请求分成两条路径。小请求进入按大小分类的空闲块，大请求单独做一次映射。释放时，小块回到它的大小类，大块解除那次映射。

两条路径的字节合成一个总数时，总数不归零也看不出是哪一条没交回。分开统计之后，每一条释放完都回到自己的零点。

语言
小请求进入大小类，超过最大类的请求使用单独映射。两条路径分开记账。

机制
不超过大小类的请求进入大小类。超过最大类的请求使用单独映射。两条路径都释放后，allocated_bytes 为 0。

程序
程序分配并释放 24 字节和 8192 字节，再读 allocated_bytes。

证明
24 字节请求和 8192 字节请求都释放之后，已分配字节为 0。

=== MEM-006
重点
线程缓存按什么尺寸归还空闲块？

背景
为减少线程争用同一个分配器，每个线程可以先在自己的缓存里按尺寸取块。这种缓存称为线程本地缓存。一个尺寸的请求不会拿到另一个尺寸的块。

别的线程释放时，块应回到上游分配器，而不是留在当初分配它的线程的缓存里。释放之后还能从那个缓存里取出同一块，说明这次释放没有走上游。

语言
缓存箱按精确请求大小存放。20 字节的空闲块不会交给 32 字节请求。

机制
线程缓存的箱按精确请求大小存放。四个线程各自分配并释放 40 个 32 字节块之后，统计中的 allocated_bytes 为 0。缓存中的 20 字节块不会返回给 32 字节请求。

程序
四个线程各自分配并释放 40 个 32 字节块，然后读取已分配字节。

证明
四个线程分配并释放 32 字节块之后，已分配字节为 0。

=== MEM-007
名词
匿名映射是一段可读可写的地址。写入的字节可以从同一地址读回。

重点
匿名映射写进去的字节，从同一地址能否读回？

背景
进程使用的是虚拟地址。程序可以向内核申请一段不对应任何文件的私有地址，写入后再从同一段地址读出。Linux 上这次申请是 mmap，不对应文件的标志是 MAP_ANONYMOUS，私有副本的标志是 MAP_PRIVATE。

读回成功只说明字节还在这段虚拟地址上。这些地址有没有对应的物理页，要看缺页和驻留，不由这一次读回决定。

语言
mmap 的 MAP_ANONYMOUS 与 MAP_PRIVATE 提供一段不对应文件的私有地址。写入后再从同一地址读出，得到的是刚写入的字节。这些页是否已经驻留物理内存，不在本节范围内。

机制
匿名私有映射上，写入 128 个字节 0x5a，同一映射的最后一个字节读回 0x5a。本节不判断这些页是否已经驻留物理内存。

程序
程序向映射写入 128 个 0x5a，再读最后一个字节。

证明
映射写入 0x5a 之后，同一映射的第 128 个字节读回 0x5a。

=== MEM-008
重点
页保护改成不可访问之后，段错误发生在哪个进程？

背景
虚拟地址按页管理。页保护决定这一页能不能读、能不写。改变调用进程某一页的保护，使用的调用是 mprotect。把页改成完全不可访问后再写入，故障发生在执行这次写入的进程上。内核向该进程投递 SIGSEGV。

子进程改保护并写入时，段错误落在子进程。父进程没有执行这次写入，所以继续运行，并能从子进程的终止状态里看到 SIGSEGV。

语言
mprotect 改变调用进程的页保护。故障信号投递给执行该写入的进程。

机制
子进程把映射改为 PROT_NONE 并写入。内核向该子进程投递 SIGSEGV。父进程继续存活，并观察到子进程因 SIGSEGV 终止。

程序
子进程把页改为 PROT_NONE 并写入。父进程检查子进程是否因 SIGSEGV 终止。

证明
子进程在 PROT_NONE 的页上写入后因 SIGSEGV 终止。父进程仍在运行并读到该终止状态。

=== MEM-009
名词
unique 独占所有权。shared 用引用计数决定析构。weak 不增加强引用。

重点
对象的析构由谁的引用计数或所有权决定？

背景
C++ 用几种智能指针区分对象由谁负责销毁。独占指针移动之后，指针留在新对象里，旧对象析构时不释放。共享指针用强引用计数，最后一个强引用离开作用域时对象析构。弱指针不增加强引用，强引用都离开之后它过期，不能再延长对象寿命。

标准库里的名称依次是 unique_ptr、shared_ptr、weak_ptr。还有强引用时对象被析构，或最后一个强引用离开后对象仍在，都是这三种计数没有对上。本节不构造强引用环。

语言
unique 转移后原指针为空。shared 的最后一个强引用离开后对象析构。weak 不延长寿命。

机制
unique 转移后，原指针为空，新指针持有对象。shared 离开作用域后，两个节点都析构。weak 不延长寿命，作用域结束后 expired 为真。

程序
程序让两个 shared 节点离开作用域，检查析构次数和 weak 是否过期，再移动 unique。

证明
作用域结束时两个节点都析构，weak 已经过期。unique 转移后原指针为空，新指针中的值是 4。

=== MEM-010
重点
0 字节请求、空指针释放和重复释放，分配器各做什么？

背景
分配器要区分三种不同的调用，不能当成同一种失败。要 0 字节，是一次没有合法大小的请求，本分配器拒绝并报错。释放空指针时，没有对应的块，什么都不做，统计不变。

同一块释放过一次后再释放，块已经不在调用方手里，这是重复释放，分配器报错，也不再把这块算进空闲。

语言
0 字节是非法请求。空指针释放是空操作。同一块的第二次释放是错误。

机制
0 字节请求抛出错误。空指针释放是空操作。同一块的第二次释放抛出错误。

程序
程序依次执行这三种调用，区分抛出错误和空操作。

证明
0 字节请求抛出错误。空指针释放没有抛出。同一块的第二次释放抛出错误。

# 进程、线程和内核可见的事实
进程拥有独立地址空间，同一进程中的线程共享地址空间。各节只核对一项内核能够观察到的事实。

=== OS-001
名词
getpid 通过系统调用向内核查询当前进程号。

重点
getpid 的返回值是什么？跟踪里应当出现哪些调用？

背景
操作系统为每个进程分配进程号。程序向内核查询自己的进程号时，得到的是线程组标识，这个值是正数。C 库提供的函数名是 getpid。

性能分析常把这次库调用记成某一次固定的系统调用。真正进入内核的名字还经过 C 库和加载器，可以和源码里的函数名不同。对不上时，以这次跟踪里出现的入口为准。没有跟踪工具时，进程号仍然可以核对。

语言
getpid 返回当前进程标识。具体进入内核的名字由 libc 和加载器决定，以本次跟踪为准。

机制
getpid 返回当前进程的正数标识。系统调用跟踪记录本次实际出现的入口。跟踪工具不存在时，观察记为不可用，返回值检查仍然有效。

程序
程序调用 getpid，要求返回值为正数。

证明
getpid 返回正数。跟踪里实际出现的调用以本次记录为准。

=== OS-002
名词
fork 之后，父子进程各自持有地址空间。子进程随后的写入，父进程看不见。

重点
fork 之后子进程写入的变量，父进程看得到吗？

背景
创建进程时，子进程要得到父进程在调用那一刻的数据副本。此后子进程修改变量，改的是自己的副本，父进程里的同名变量保持调用前的值。完成这次创建的调用是 fork。

Linux 常用写时复制实现这份副本：先共享物理页，有一方写入时才复制。父进程仍看到旧值，只说明写入留在子进程一侧。本节没有读取缺页次数，不能把结果写成已经测到了写时复制。

语言
fork 之后，子进程对自己这份数据的写入，父进程看不到。Linux 的 fork(2) 用 copy-on-write 实现这种隔离。本课只看到父进程的变量仍是 1，没有读取缺页次数，所以不把结果写成已经测到了写时复制。

机制
子进程在 fork 之后把变量改为 2 并退出。父进程中的同一变量保持为 1。地址空间分离解释这次隔离。缺页次数不能单独证明写时复制。

程序
子进程把变量改为 2。父进程检查自己的变量是否仍为 1。

证明
子进程把变量写成 2 并正常退出。父进程中的同一变量仍是 fork 之前的 1。

=== OS-003
名词
同一进程里的线程用 tid 区分。

重点
两个线程怎样区分？

背景
一个进程里可以有多个线程。它们共享地址空间，进程号相同。日志只打印进程号时，多个线程的输出叠在一起。每个线程还有自己的线程标识。

创建线程的接口是 pthread_create。查询进程号用 getpid，得到的是线程组标识。查询线程自己的标识用 gettid。两个线程都创建成功后，两个线程标识都是正数，并且彼此不同。本节不描述内核任务结构体的字段。

语言
Linux 的 gettid 返回调用者的线程标识。同一进程里的两个线程是两个任务，tid 不同。getpid 返回的是线程组标识。本节不描述 task_struct。

机制
Linux 为每个任务分配不同的 tid。父线程与新线程的 tid 都为正数，并且互不相等。本节不描述 task_struct 的布局。

程序
程序读取父线程和新线程的 tid，要求二者为正数且不相等。

证明
父线程与新线程的 tid 都为正数，并且互不相等。

=== OS-004
名词
同一进程的线程看见同一段地址。fork 出来的子进程有自己的地址空间。

重点
一次写入对线程可见，还是对子进程可见？

背景
线程和进程对内存的可见性不同。同一进程里的线程共享地址空间，一个线程写入后，另一个线程在汇合之后能读到。fork 创建的是新进程，子进程后来的写入留在自己的地址空间，不回到父进程。

一次写入只在一部分执行流里出现时，先区分这些执行流是线程还是进程。本节先做线程写入，再做子进程写入。

语言
同一进程的线程共享地址空间。fork 出的子进程不把随后的写入发布回父进程。

机制
同一进程的线程共享地址空间，新线程写入的 1 在 join 之后对原线程可见。fork 出的子进程写入 5，不改变父进程中的 1。

程序
程序先让新线程写入并 join，再让子进程写入并检查父进程中的值。

证明
新线程写入的 1 在 join 之后可见。子进程写入的 5 不改变父进程中的值。

=== OS-005
重点
条件变量返回时，等待者看到的是哪一次写入？

背景
线程等待某个条件成立时，叫醒只表示“可能有变化”，不代替条件本身。这个条件称为谓词。通知方要在持有互斥量时写下新谓词，再通知。等待方要在持有同一把互斥量时查看。谓词仍是旧的，就继续等。

从等待返回后再次持锁查看，这时读到的才是已经写下的新值。通知不携带这份数据。通知太早或被白白叫醒，都靠这次复查滤掉旧值。本节不证明底层是否真的进入睡眠。

语言
等待者在持锁时检查谓词。通知本身不代替谓词。伪唤醒要靠再次检查滤掉。

机制
等待者在持锁状态下反复检查谓词 value == 7。通知方在持锁时把 value 设为 7 再通知。等待者返回时谓词已经成立。伪唤醒由谓词复查挡住。本节不证明 futex 进入了睡眠。

程序
通知方在持锁时把 value 设为 7。等待线程返回后，程序核对 value。

证明
等待线程返回时，持锁发布的 value 已经是 7。

=== OS-006
重点
线程的 CPU 亲和性掩码是否已经设置成功？

背景
调度器只把线程放到允许的 CPU 上。这个允许集合称为亲和性掩码。设置它的调用是 sched_setaffinity，读回它的调用是 sched_getaffinity。

把掩码收成只含 CPU 0 之后，读回的掩码里有 CPU 0，说明内核已经接受设置。调度器仍可能稍后再把线程放上去。掩码里有某颗 CPU，不等于下一条指令已经在那颗 CPU 上执行。设置失败时，这台机器不能完成这项观察。

语言
sched_setaffinity 修改的是允许运行的 CPU 集合。调度器仍可推迟实际上 CPU。

机制
sched_setaffinity 把掩码设为只含 CPU 0 之后，sched_getaffinity 读回的掩码包含 CPU 0。调度器仍可能推迟该线程实际上 CPU。设置失败时，本节记为当前主机不能完成这项观察。

程序
程序把掩码设为只含 CPU 0，再读回并检查 CPU 0 是否在掩码中。

证明
读回的亲和性掩码包含 CPU 0。

=== OS-007
重点
yield 之后，自愿切换计数一定会增加吗？

背景
线程可以主动让出处理器，让调度器考虑运行别人。这个提示是 sched_yield。内核把自愿让出后发生的切换次数累计起来，getrusage 里的字段名是 ru_nvcsw。

负载、时间片和计数粒度都会影响这一次有没有被记上。连续让出很多次，前后的差值仍可以是 0。差值为 0 不能说明切换没发生，也不能说明一定发生了。它只是一份样本。

语言
ru_nvcsw 是内核报告的自愿切换次数。差值为 0 仍是一次有效样本。

机制
连续 1000 次 sched_yield 前后，ru_nvcsw 的差值是内核报告的自愿切换样本。差值为 0 仍然是有效样本，不能据此判定切换没有发生或一定发生。

程序
程序在 1000 次 sched_yield 前后读取 ru_nvcsw，记录差值。

证明
1000 次 sched_yield 前后的 ru_nvcsw 差值已经记录。差值为 0 也是一次有效样本。

=== OS-008
名词
管道传递字节。MAP_SHARED 映射让父子进程看见同一段内存里的写入。

重点
管道里的字节和共享映射里的写入，父进程各能看见什么？

背景
进程之间传数据有两种常见方式。一种是字节流：写入的字节按顺序被读出，流本身不保留一条消息的边界。管道就是这种字节流。另一种是共享同一段物理页：一边写入，另一边从同一映射读到。把匿名映射成这样共享的标志是 MAP_SHARED。

数据没有到达时，先分这次用的是管道里的字节，还是这段共享内存。

语言
管道传递字节流。MAP_SHARED 匿名映射把写入发布到映射同一段的其他进程。

机制
管道写入两个字节 ok 后，读端得到同样的字节。MAP_SHARED 匿名映射上，子进程写入 42，父进程读到 42。

程序
程序写两个字节到管道并读回，再让子进程向共享映射写入 42。

证明
管道读回写入的两个字节。MAP_SHARED 映射上，父进程读到子进程写入的 42。

=== OS-009
名词
信号到达后，已经安装的处理函数会执行。

重点
raise 之后，处理函数有没有执行？

背景
信号是内核投递给进程的异步通知。处理函数要先安装好，信号递达时才会执行。安装处理函数的调用是 sigaction。向当前进程发信号的调用是 raise。

语言
sigaction 安装的处理函数在该信号递达时执行。处理函数仍受异步信号安全约束。

机制
sigaction 安装 SIGUSR1 的处理函数后，raise 使该函数执行一次，delivered 变为 1。处理函数仍然受异步信号安全约束。

程序
程序为 SIGUSR1 安装处理函数并 raise，检查 delivered 是否为 1。

证明
SIGUSR1 的处理函数执行了一次，delivered 为 1。

=== OS-010
重点
这台机器有几个可见的 NUMA 节点？

背景
多处理器机器可以把内存分成若干节点，访问本节点和跨节点的延迟不同。这种结构称为 NUMA。要比较跨节点延迟，至少要有两个看得见的节点。

Linux 把每个节点放在 sysfs 的 /sys/devices/system/node 下。目录少于两个，就没有第二条节点可测，结果不能写成延迟比较。目录够数时，本节只记录个数，不绑定内存，也不测量延迟。

语言
跨节点延迟比较至少需要两个节点。节点数来自 sysfs，不来自耗时猜测。

机制
sysfs 中可见的节点目录少于两个时，主机不能做跨节点比较，结果为不支持。节点不少于两个时，本节只记录节点数量，不绑定内存，也不比较延迟。

程序
程序统计 node 目录。少于两个时结果为不支持，不少于两个时只记录数量。

证明
可见 NUMA 节点不少于两个。本次只记录节点数，不比较延迟。

# 锁
每种锁只保证自己声明的互斥、顺序或次数。各节用计数或到达数核对一种锁的一项性质。

=== SYNC-001
重点
测试并设置锁包住的递增，总和是多少？

背景
多线程改同一个计数时，要用锁把临界区里的加一串起来。测试并设置自旋锁用一次原子交换进入临界区：空闲是 0，成功把 0 换成 1 的线程进入，其他线程看到 1 就继续自旋。释放时再写回 0。获取用的顺序是 acquire，释放用的顺序是 release。

它不记录谁先到达，所以先到的线程不一定先进入。临界区里的递增被串起来之后，最终计数等于线程数乘以每个线程的次数。先到先服务不在通过条件里。

语言
这把教学自旋锁未锁为 0，已锁为 1。获取用 acquire 把值换成 1，释放用 release 存入 0。它不公平，不按到达顺序服务。

机制
四个线程在同一把测试并设置锁内各递增 2000 次。临界区结束时计数为 8000。这把锁不保证先到先服务。

程序
四个线程各在锁内递增 2000 次，程序核对最终计数。

证明
四个线程在测试并设置锁内各递增 2000 次，计数为 8000。

=== SYNC-002
重点
票据锁的互斥由哪两个数维持？

背景
有的锁按到达顺序把临界区交给下一个线程。票据锁用两个数维持这个顺序：一个数负责发号，一个数表示当前轮到谁。发号是 relaxed 的 fetch_add。轮到的号在解锁时用 release 发布，等待的一方用 acquire 读取，直到轮到自己才进入。

只看最终计数，只能说明加一没有丢，看不出谁先进入。本节先固定两个线程的取号顺序，再核对进入顺序，并用四线程递增核对互斥。这把锁不可重入。

语言
取号计数用 relaxed fetch_add 发号。服务号在解锁时用 release 发布，自旋侧用 acquire 读取。对已经取到号的线程，这把教学锁按票号交接，并且不可重入。

机制
主线程先持有锁。第一个线程取到下一号并等待，第二个线程再取号。主线程解锁后，先取号的线程先进入。四个线程另各递增 2000 次，计数为 8000。

程序
程序先固定取号顺序并核对进入顺序，再让四个线程各递增 2000 次。

证明
先取号的线程先进入。四个线程各递增 2000 次，计数为 8000。

=== SYNC-003
重点
MCS 锁的队列节点必须活到什么时候？

背景
队列锁让等待者在自己的节点上自旋，而不是都去抢同一个标志。MCS 锁就是这种队列锁。解锁时要读这个节点，才能找到下一个人，或确认后面没有人。因此节点在解锁返回之前必须还在，并且只由这个线程使用。

解锁返回之后，节点不再挂在队列上，同一个节点可以再次加锁。把节点放在守卫内部，是为了让它的寿命盖住这次解锁。本节没有在解锁返回前销毁节点，一次正常返回不能代替那个用例。

语言
等待者自旋在自己的节点上。节点在 unlock 返回前必须仍然有效。

机制
程序用同一节点加锁、解锁，再加锁、解锁。随后四个线程用 McsGuard 各递增 1000 次，计数为 4000。本节不构造 unlock 返回前销毁节点的用例，因此一次未崩溃不能代替那个用例。

程序
程序在 unlock 返回后用同一节点再次加锁，再让四个线程各递增 1000 次。

证明
同一节点在 unlock 返回后再次加锁成功。四个线程各递增 1000 次，计数为 4000。

=== SYNC-004
名词
互斥量在同一时刻只允许一个线程留在临界区里。

重点
这把 futex 互斥量保护下的计数是多少？

背景
互斥锁可以用一个机器字记住自己处在哪一步。这把教学锁用三种值：0 是空闲；比较交换把 0 改成 1，表示已经锁上、还没有公布等待者；后来的线程把值换成 2 再等，2 表示已经锁上并且有人在等。持有者解锁时若看到 2，就叫醒一个等待者。

四个线程的加一都在锁里完成时，计数等于全部次数。慢路径计数增加，只说明没能马上锁上，不说明线程已经在 futex 上睡着。这不是 POSIX 对所有互斥量规定的状态编码。

语言
这把教学互斥量用一个字表示三态：0 未锁，1 已锁且没有公布等待者，2 已锁且有等待者。快路径从 0 比较交换到 1。慢路径换入 2，并在字为 2 时等待。这不是 POSIX 对所有互斥量的状态编码。是否进入睡眠由 SYNC-010 计数。

机制
四个线程在这把互斥量内各递增 2000 次，计数为 8000。慢路径是否进入睡眠由 SYNC-010 单独计数。

程序
四个线程各在锁内递增 2000 次，程序核对最终计数。

证明
四个线程在 futex 互斥量内各递增 2000 次，计数为 8000。

=== SYNC-005
重点
已经排队的写者，会不会被后到的读者插到前面？

背景
读写锁允许多个读者同时持有，写者则独占。谁在对方正在等待时可以插队，是这把锁的策略。本实现看到已有写者在等，就不让新的读者进入，避免读者一直到来把写者饿死。共享持有者离开后，排队的写者先进入。

一个写者单独把计数加到某个值，并不能说明第二个写者被挡住，也不能说明后来的读者没有插到前面。本节先排好一个写者和一个后到的读者，再让两个写者同时递增。POSIX 还允许别的优先策略。

语言
已有写者等待时，新读者不能进入。这是这个实现的写优先。POSIX 读写锁还有其他合法策略。

机制
主线程持有共享锁。写者先排队，后到的读者也排队。主线程放开共享锁之后，写者先进入，读者在写者离开后才进入。另有两个写者各递增 100 次，计数为 200，同时持有写锁的线程数不超过 1。

程序
程序先排好一个写者和一个后到的读者，核对进入顺序，再让两个写者各递增 100 次。

证明
后到的读者在已排队的写者之后进入。两个写者的计数为 200，写锁没有重叠。

=== SYNC-006
重点
同一线程能否再次锁住递归互斥量？

背景
普通互斥量不允许持有者再获取一次。同一线程再次加锁，会一直等自己放开，于是卡住。递归互斥量记住持有者是谁，以及已经加锁几次。持有者再加一次，次数增加，它可以继续执行。每放一次，次数减一。

次数还没减到零，其他线程不能进入。减到零之后，其他线程才能拿到。本节由持有者重入，并核对其他线程在完全放开之前不能进入。

语言
重入只对当前持有者有效。其他线程仍被这把锁互斥。

机制
拥有者线程可以连续 lock 两次，再 unlock 两次。其他线程之间仍然互斥。四线程计数为 2000。非拥有者不能借用递归计数进入临界区。

程序
持有者连续 lock 两次再 unlock 两次。随后四线程各递增 500 次。

证明
同一线程连续加锁两次并解锁两次。随后四线程在递归互斥量内的计数为 2000。

=== SYNC-007
重点
等到锁之后，读到的谓词是通知前的旧值吗？

背景
线程拿到互斥量，只表示现在可以读共享状态，不表示状态已经是对方写下的新值。等待条件成立时，要在持锁期间查看这个条件，条件不成立就放开锁并等待。对方随后持锁写下新值，再通知。

被叫醒的线程重新拿锁，这时读到的才是已经写下的值。它在重新查看之前就使用共享数据，用的仍是等待前的旧值。通知只负责叫醒。

语言
谓词在持锁期间写入，等待者在持锁期间复查。伪唤醒不代替这次复查。

机制
谓词 value == 7 在持锁期间发布，等待者在持锁期间复查。等待线程返回时 value 为 7。允许伪唤醒。本节不证明 futex 一定睡眠。

程序
通知方把 value 设为 7 后通知。等待线程返回后程序核对 value。

证明
等待线程返回时，持锁发布的谓词 value 为 7。

=== SYNC-008
重点
同时持有的许可能不能超过信号量初值？

背景
信号量用一个计数限制同时使用某项资源的线程数。这个初值就是许可的张数。成功获取，手头多一张，计数少一张。再获取会越界时，线程等待，不能进入。释放把许可还回去。

同时拿在手里的许可超过初值，表示有线程在没有许可时使用了资源。等待队列公不公平，是另一件事。本节核对同时存在的许可不超过初值。

语言
信号量用计数限制同时进入的线程数。调度没有重叠时，观察到的并发可以小于初值。

机制
信号量初值为 2。四个线程反复获取许可，观测到的最大并发不超过 2。调度没有让两个持有者重叠时，最大并发小于 2 仍然通过。超过 2 才是失败。

程序
初值为 2。四个线程反复获取许可，程序记录观察到的最大并发。

同时持有的许可数不超过初值 2。

=== SYNC-009
重点
屏障返回时，每个线程看到多少个到达者？

背景
屏障让一组线程等全体到齐再继续。先到的线程记下自己的到达并等待。最后一个人到达后，到达人数成为全体人数，并发布新的一代。等待的线程看到代数变化才返回，然后再读到达人数。

这时每个线程读到的是大家都到了的数。在放行前去读，看到的是还没有到齐的人数。本节用四个参与者核对返回后的到达数。

程序

=== SYNC-010
重点
慢路径计数和只执行一次，各说明什么？

背景
互斥量没马上拿到时，会走慢路径：快速比较交换失败，计数加一，然后才可能在 futex 上等待。这个计数大于 0，只说明快路径没成功，不说明已经睡着。

只执行一次的初始化是另一套状态。第一个线程执行初始化函数，后来的线程看到已经完成，函数体不再进入。标准库里的对应物是 call_once。八个线程同时调用时，函数体只执行一次。

语言
slow_path_count 在快速比较交换失败时增加。OnceFlag 保证初始化函数只进入一次。

机制
锁已被持有时，另一个线程进入 Mutex 的慢路径，slow_path_count 在解锁前大于 0。该计数在快速比较交换失败时增加，不证明 futex 已经睡眠。八个线程调用 OnceFlag，初始化函数只进入一次。

程序
程序在锁已被持有时等慢路径计数变为非 0，再让八个线程调用 call_once。

证明
锁已被持有时，slow_path_count 在解锁前大于 0。八个线程的初始化函数只进入一次。

# 原子操作与内存序
原子性、发布顺序和回收时机是三项不同的约束。各节只证明其中一项，样本次数写在该节里。

=== AT-001
名词
共享计数在互斥量保护下修改。结果由语言的数据竞争规则规定。

重点
有定义的共享计数应等于多少？

背景
多个线程同时改一个普通整数，如果没有任何同步把两次访问排开，语言就不规定结果。这种未同步的冲突访问称为数据竞争，规定写在 [intro.races]，行为无定义。把“谁先谁后”排开的关系称为 happens-before。同一把互斥量上，先发生的解锁和后来的加锁构成这种关系。

加一放在这把锁里，每一次都留得下，计数等于全部次数。这条路没有崩溃，只说明锁里的计数有定义。本节不运行不加锁的那条路，所以不能用“没崩溃”证明那条路没有数据竞争。

语言
[intro.races] 规定：两个可能并发的冲突访问，至少一个不是原子操作，且没有 happens-before，就是数据竞争，行为无定义。同一把 mutex 上，先发生的 unlock 与之后的 lock 同步。本节只运行互斥量保护下的递增。它不运行数据竞争那条路径，所以一次未崩溃不能证明没有数据竞争。

机制
四个线程在互斥量保护下各递增 1000 次，计数为 4000。未同步的普通整数递增是数据竞争。本节不运行那条路径，因此一次未崩溃不能证明不存在数据竞争。

程序
四个线程在锁内各递增 1000 次，程序核对计数是否为 4000。

证明
四线程在互斥量保护下各递增 1000 次，计数为 4000。

=== AT-002
名词
内存序是加在原子操作上的顺序约束，规定这次操作与其他内存访问之间能否重排、能否构成同步。relaxed 是其中最弱的一种。

重点
只要求原子性的递增，总和正确时，其他普通数据是否也已经可见？

背景
在 C++ 内存模型中，一个线程写入内存之后，另一个线程何时能看到这次写入，以及这次看到能否带上此前的其他写入，由内存序约束。内存序附在原子加载、存储或读改写上。编译器和处理器按照它，决定该原子操作能否与前后的普通内存访问重新排序，以及它是否与另一线程的原子操作同步。C++ 标准在 [atomics.order] 中列出这些约束，并用 memory_order 作为它们的名称。

其中最弱的一种是 memory_order_relaxed。它只要求这一次读、改、写作为整体完成，不被别的线程从中间拆开。多个线程对同一原子变量做 fetch_add 时，递增不会互相覆盖丢失。全部次数完成之后，计数等于次数之和。relaxed 不要求这次操作与其他普通内存建立 happens-before。因此计数已经正确时，另一线程仍可能观察到与这次递增同时写下的普通数据的旧值。总和说明的是原子性，不是那些普通写入已经可见。

语言
[atomics.order] 中的 memory_order_relaxed 只约束该原子读改写本身：操作是原子的，但不与其他普通内存建立 happens-before。

机制
relaxed fetch_add 保证读改写的原子性。四线程共 40000 次之后计数为 40000。relaxed 不建立与其他内存的 happens-before。

程序
四个线程共执行 40000 次 relaxed fetch_add，程序核对总和。

证明
40000 次 relaxed fetch_add 之后，计数为 40000。这次总和只证明原子性。

=== AT-003
重点
旗标变为 1 之后，载荷必须是多少？

背景
内存序里，比只保证原子性的 relaxed 更强的两种用于发布和观察。用于存储的那一种，要求这次存储之前的写入能被后来同步上来的读取一起看到，名称是 memory_order_release。用于加载的那一种，若读到的值来自一次 release 存储，则那次 release 之前的写入对这次加载之后的读取可见，名称是 memory_order_acquire。

用旗标发布数据时，先用 relaxed 写下载荷，再用 release 把旗标写成 1。对方用 acquire 看到旗标为 1 之后再读载荷，载荷应是旗标之前写入的值。旗标已经为 1 而载荷仍是更早的旧值，说明存储不是 release，或加载不是 acquire。

语言
[atomics.order] 规定：release 存储与后来读到该值的 acquire 加载同步。排在这次 release 之前的写入，对 acquire 之后的读取可见。本节先用 relaxed 写入载荷 42，再用 release 写入旗标 1。

机制
写线程用 relaxed 写入载荷 42，再用 release 写入旗标 1。读线程用 acquire 看到旗标为 1 之后，载荷为 42。重复 200 次。这是语言内存模型的要求。

程序
写线程先存 42 再 release 旗标。读线程 acquire 到旗标后读取载荷。重复 200 次。

证明
200 次试验中，acquire 看到旗标为 1 之后，载荷都是 42。

=== AT-004
重点
seq_cst 是否允许两个加载同时看到 0？

背景
处理器可以把写入暂时留在自己的缓冲里，稍后再让别的线程看见。两个线程各自先写自己的变量、再读对方的变量时，两边的写入都还在本地缓冲中，两个读取会同时看到 0。这是存储缓冲能够出现的一种交错。

内存序里最强的一种为参与的原子操作建立总顺序，名称是 memory_order_seq_cst。使用它时，这次试验不允许两个加载同时为 0。relaxed 和 acquire/release 仍允许这个结果。出现双零时，先看用的是哪一种内存序。更弱顺序下的双零不记成 seq_cst 失败。

语言
[atomics.order] 的 seq_cst 为这些操作建立总顺序。本次试验不允许两个加载同时为 0。relaxed 或 acq_rel 允许该结果，本节不把那种结果当成失败。

机制
seq_cst 不允许这次存储缓冲结果中两个加载同时为 0。300 次试验中不出现该结果。relaxed 或 acq_rel 允许该结果，本节不把那种允许的结果当成失败。

程序
两个线程各写自己的变量再读对方的变量。300 次中不得出现双 0。

证明
300 次 seq_cst 试验中，没有出现两个加载同时为 0。

=== AT-005
重点
seq_cst 的 IRIW 样本里，哪一组结果被禁止？

背景
四个线程可以分成两名写入者和两名读取者。两名写入者各写一个变量，两名读取者用不同的顺序去读这两个变量。若每个读者都先看见对方的写入、同时看不见本应更早看见的那一次，两组观察就互相矛盾。这个场景通常称为 IRIW。

seq_cst 禁止这组交叉。一批试验里没有出现，只说明这批样本里没有。编译器、处理器和试验次数都可能让一次运行碰不到它。没有出现，不能写成每一次执行都不会出现。

语言
被禁止的一组是 r1=1、r2=0、r3=1、r4=0。没有出现只说明这 200 次样本。

机制
seq_cst 禁止 r1 为 1、r2 为 0、r3 为 1、r4 为 0 这一组结果。200 次没有出现，只说明这批样本没有违反约束。

程序
四个线程按 IRIW 形状使用 seq_cst。程序检查该组结果是否出现。

证明
200 次样本中没有出现被 seq_cst 禁止的那组交叉结果。

=== AT-006
重点
release/acquire 栅栏怎样把载荷传过去？

背景
内存序除了写在每次原子操作上，也可以单独插在两条访问之间，用来限制编译器和处理器怎样重排。C++ 里这种栅栏是 atomic_thread_fence。它和某一种机器上的 dmb、mfence 不是同一个对象。

release 栅栏放在载荷的普通原子存储之后、旗标存储之前。acquire 栅栏放在看见旗标之后、读取载荷之前。这样，读到的载荷是旗标之前写下的值。只把操作标成 relaxed、栅栏没有成对，旗标为真仍可能读到旧载荷。

语言
这里核对的是 C++ 的 atomic_thread_fence。它和编译器屏障、ISA 屏障不是同一个对象。

机制
写线程在 relaxed 存储载荷之后执行 release fence，再 relaxed 存储旗标。读线程看到旗标后执行 acquire fence，再读取载荷。重复 200 次，载荷为 42。这里核对的是 C++ 的 atomic_thread_fence。

程序
写线程在载荷之后放 release fence，读线程在旗标之后放 acquire fence。重复 200 次。

证明
200 次试验中，acquire fence 之后读到的载荷都是 42。

=== AT-007
重点

背景
无锁结构回收节点之后，分配器可能把同一地址再交给一个新节点。比较交换如果只比较地址，会以为等着的仍是原来那个节点，交换成功，新节点被当成旧节点接进去。这个现象称为 ABA。

把地址和一个版本号放在同一个字里，节点换代时版本改变。再拿旧版本去比较交换，比较失败，新节点不会装到旧位置上。本节核对版本变化之后，旧的期望值不能交换成功。

本节用一个 64 位字的高 32 位做版本号。第一次比较交换把版本从 0 改为 1。随后仍用版本 0 的期望值做比较交换，必须失败，低 32 位保持为 1。这是版本号使旧期望失效的演示。

程序
程序先把版本从 0 改为 1，再用版本仍为 0 的期望值做比较交换。

证明
版本号从 0 改为 1 之后，仍携带版本 0 的比较交换失败，字的低 32 位保持为 1。

=== AT-008
重点
相邻原子和按缓存行分开的原子，计数都能完成吗？

背景
处理器以缓存行为单位在核之间保持内存一致。两个线程各自递增挨得很近的原子变量时，两个变量可能落在同一条缓存行上。一个核写入，会使另一个核上的那一行失效，耗时变长。这种现象称为伪共享。

按缓存行把它们分开之后，写入不再失效对方那一行。比较耗时之前，两边的加法都要做完，否则两次时间对应的工作量不同。地址间隔不够一条缓存行，也不能说它们已经分开。耗时只是一次样本。

语言
耗时差属于微架构。通过条件只要求两种布局的递增都完成。

机制
相邻布局和按缓存行填充的布局都完成递增，两次之和都是 400000。耗时差取决于微架构，不作为通过条件。

程序
两种布局各由两个线程递增，程序核对两次之和都是 400000。

证明
相邻布局和填充布局的递增之和都是 400000。耗时只作为样本记录。

=== AT-012
重点
危险指针仍发布某个地址时，这个地址会被回收吗？

背景
无锁结构里，读者还在使用某个地址时，回收方不能把这块内存交还。危险指针的做法是：读者先把正在使用的地址公布出来。回收方看到这个地址仍被公布，就跳过它。读者取消公布之后，回收才可以释放。

地址还公布着就被释放，读者接下来的访问用的是已经交还的内存。本节核对仍被公布的地址是否被跳过。

语言
回收扫描会跳过仍被危险指针发布的地址。阈值是本教学域的槽数乘以最大线程数。

=== AT-013
重点
线程处于 pin 期间，刚退役的对象会被删除吗？

背景
另一种保护读侧的办法是让读者先声明“我还在用”，这段声明常称为 pin。删除必须发生在读者取消声明之后。声明还在时就把对象交给回收，读者返回时用的是已经删除的对象。

机制
线程处于 pin 期间退役一个对象，删除计数为 0。unpin 后再退役两个对象，删除计数为 2。最后一个对象可以留到下一次宽限期。

证明
pin 期间退役一个对象后，删除计数为 0。unpin 后再退役两个对象，删除计数为 2。

=== CACHE-001
重点
顺序访问和跨步访问的校验和是否都成立？

背景
处理器访问内存以缓存行为单位。循环的步长决定连续几次访问落在哪些行上。数组元素等于下标时，步长 1 累加的是连续下标，步长 16 累加的是另一批下标。两种和不同，但都可以按步长算出来。

跨步碰到的缓存行重叠更少，耗时可以更长。频率、预取和当时的其他程序也会改变这一次耗时。和不等于按步长算出的结果，是漏加或重复加了元素，不是缓存快慢所能解释的。谁更快不是通过条件。

语言
谁更快不是语言规则，也不作为通过条件。CPU 型号记在环境快照里。

机制
数组元素等于下标。步长 1 的校验和是 4 次 0 到元素数减 1 的和。步长 16 的校验和是 4 次这些下标的和。只要求非 0 会放过少加元素的错误。一次耗时是样本。谁更快不作为通过条件。

程序
程序用步长 1 和步长 16 各走一遍数组，把校验和与按步长累加的结果比较，并记录耗时。

证明
顺序访问和跨步 16 的校验和分别等于按步长累加的结果。耗时只作为一次样本记录。

=== CACHE-002
重点
一次复制之后，目的缓冲区是否与源缓冲区相同？

背景
把一块内存抄到另一块，抄完之后目的地的每个字节都应和源相同。完成这次按长度复制的库函数是 memcpy。源缓冲事先写入已知内容，目的缓冲在复制前是别的内容。

证明
8 MiB 复制之后，目的缓冲区与源缓冲区逐字节相同。耗时只作为一次样本记录。

# 协程和 fiber
fiber 在 yield 处让出，协程在挂起点让出，工作窃取按区间分派下标。各节只核对自己的顺序或总和。

=== CO-001
重点
两个 fiber 在什么位置交替？

背景
有一种执行流完全在用户态切换，内核不会用时间片抢占它。它要自己让出，调度器才去运行另一个。这种执行流称为 fiber，让出的点称为 yield。

前一个 fiber 没有执行到 yield，后面的 fiber 就没有机会运行。两个 fiber 都在 yield 把控制交出去之后，输出才按让出的位置交替。fiber 不是内核线程。

语言
yield 把当前 fiber 挂起并运行另一个。不调用 yield 的 fiber 不会被抢占。

机制
两个 fiber 在 yield 处交替，日志为 A1B1A2B2。不调用 yield 的 fiber 不会被抢占。这是 ucontext 切换，不是内核线程。

程序
程序运行两个 fiber，核对日志是否为 A1B1A2B2。

证明
两个 fiber 在 yield 处交替，日志为 A1B1A2B2。

=== CO-002
重点
协程在挂起点怎样交替？异常从哪里重新抛出？

背景
协程执行到挂起点时把控制交还调用方，调用方可以先做别的事。恢复之后，协程从那个挂起点继续。它不是线程。协程体内抛出的异常先留在协程里，要到负责驱动它的 run 结束时，才重新抛给调用方。

调用方在 run 返回之前看不到这个异常，会以为任务已经正常结束。两个协程的输出顺序，由它们在挂起点让出的次序决定。

语言
协程在调度器恢复之前不运行，也不自动变成线程。

机制
两个协程在挂起点交替，日志为 ACBD。任务抛出 runtime_error 时，run 重新抛出该异常。协程在调度器恢复之前不运行，也不自动并行。

程序
程序核对日志 ACBD，并检查 run 是否重新抛出 runtime_error。

证明
两个协程在挂起点交替，日志为 ACBD。run 重新抛出任务中的 runtime_error。

=== CO-003

工作窃取算出的总和是否等于区间公式？

工作窃取把一个大区间拆成多段，空闲的执行者从别人那里取走还没做的段。用来求和时，每段把自己的下标加完，汇合之后应等于从头到尾串行相加的结果。某一段没执行，总和就少一截。

某一段里抛出的异常如果在汇合之前被忽略，调用方既看不到完整的和，也不知道哪一段失败。汇合之后把异常重新抛出，失败的那段才到达调用方。

机制
工作窃取把 0 到 999 分给工作者，总和等于 999 * 1000 / 2。每个工作者使用自己的双端队列。被窃取的下标仍然来自这个区间。

先建立用户命名空间并映射为 0。随后分别核对 PID、挂载、UTS 和网络命名空间，再核对 chroot 与地址空间上限。主机不能建立所需命名空间时，结果记为不支持。

=== STO-002
名词
页是一段固定长度的文件区间。页号乘以页长等于该页的文件偏移。

重点
写入页号 1 之后，页号 0 的字节是否保持原值？

背景
数据库常把文件切成固定长度的页。页号乘以页长，就是这一页在文件里的起点。下一页从这一页的结尾再开始，两页的区间不能重叠。

第 0 页和第 1 页写成不同的字节之后，按页号 1 去读，应当落在第二页，读回第二页的字节。页号或页长用错，读到的是旁边那一页。本机页长来自 sysconf，算式仍是页号乘以页长。

语言
页长来自 sysconf(_SC_PAGESIZE)。pread 和 pwrite 使用这个偏移，不依赖当前文件位置。

机制
页号 n 的起始偏移是 n 乘以页长，区间是 [n * page_size, (n + 1) * page_size)。写入页号 1 只覆盖这个区间，不改页号 0。页长是 sysconf(_SC_PAGESIZE) 的返回值，同一次会话的环境快照用 page_size 记录它。OS-008 核对管道和 MAP_SHARED 中的字节。本课核对按页号定位的两个文件区间。填数观察可以改页长和页号，本机执行仍使用系统页长，并写入 0xA1 与 0xB2。

程序
程序比较页号 1 的整页是否为 0xB2，以及页号 0 的整页是否仍为 0xA1。

证明
页号 1 读回 0xB2，页号 0 仍是 0xA1。

=== STO-003
名词
索引项保存键、载荷偏移、载荷长度和占用标记。

重点
键 beta 是否读到它自己的载荷，键 delta 是否没有索引项？

背景
索引的作用是从键找到记录在文件中的位置。命中时，返回的是这个键自己的偏移，再按偏移读出内容。键不在索引里，就没有偏移可返回，不能把文件开头的字节当成它的记录。

两个键落到同一个槽时，仍要用键本身区分这个偏移属于哪一次查找。本节分开命中的偏移和缺失的键。

语言
索引是 4 个定长项。键按 8 字节比较，不足的部分补 0。

机制
alpha、beta、gamma 占用前三个项，载荷放在索引区之后。查找扫描占用项。delta 没有占用项，因此不返回偏移。本课的页和偏移关系见 STO-002。

程序
程序查找 beta，并检查载荷是否为 BETA。再查找 delta，并检查它没有命中。

证明
beta 的载荷是 BETA。delta 没有索引项。

=== STO-004
名词
加锁顺序是多个互斥量的获取次序。相反的次序会让两个线程各自持有一把锁并等待另一把。

重点
相反顺序是否在超时后放弃更新？相同顺序是否完成两次更新？

背景
同时改两行记录时，每行各有一把锁。若一个执行者先拿第 0 把再等第 1 把，另一个先拿第 1 把再等第 0 把，两边都握着对方正在等的锁。带超时的加锁会等到超时。这里使用的是 pthread_mutex_timedlock。

两边都先拿编号较小的锁，再拿另一把，等待不会这样交叉，两次更新都能完成。这个顺序是程序约定的。本节不扫描全部的锁，也不另做死锁检测。

语言
pthread_mutex_timedlock 在绝对期限到达时返回 ETIMEDOUT。期限是 300 毫秒。

机制
相反的获取次序使每条线程持有对方正在等待的锁，期限内没有人释放，所以更新不会写入。相同次序把两把锁排成全序，后到的线程在前一个线程释放之后进入临界区，两次更新都能完成。互斥量的持有关系见 SYNC-004。

程序
程序先跑相反顺序，再跑相同顺序，并核对更新计数。

证明
相反顺序的更新计数是 0。相同顺序完成后更新计数是 2。

=== STO-005
名词
预写日志（write-ahead log）先追加日志再修改页。本课页上的 applied_lsn 充当 pageLSN，也就是已经应用到该页的最后一条日志的 LSN。

重点
完整日志重放后页是什么？把日志截断到已提交记录再重放，页是否回到那条记录？

背景
为了崩溃之后还能恢复，更新先把记录按序号追加到日志，再改数据页。页上记下已经应用到的最大序号。重放时，序号不大于这个值的记录已经在页上，应当跳过。这个页上序号的作用，与 ARIES 里的 pageLSN 相同。本课的字段名是 applied_lsn。

日志在某个序号之后被截断，更大的记录不会再写到页上。本节没有分析阶段，没有撤销，也没有脏页表。

语言
每条日志记录包含 lsn、页内偏移和 4 个字节。追加后调用 fsync。fsync 失败时结果为不支持。

机制
重做时只应用 LSN 大于 pageLSN 的记录。第一条记录把偏移 0 写成 ABCD 并应用到页，applied_lsn 变为 1。第二条记录把偏移 4 写成 EFGH，只进入日志。重放后页是 ABCDEFGH，applied_lsn 为 2。再把页恢复成 lsn 1 的镜像，并把日志截断到第一条记录末尾，重放保持 ABCD....。这是 pageLSN 比较，加上一次日志截断。ARIES 还有分析、重做、撤销和脏页表，本课没有这些阶段。页的定位见 STO-002。

程序
程序比较两次重放后的 8 个字节和 applied_lsn。

证明
完整日志重放得到 ABCDEFGH，applied_lsn 为 2。截断后再重放得到 ABCD....，applied_lsn 为 1。

=== SRV-002
名词
长度前缀帧由 4 字节大端长度和随后的载荷组成。长度或载荷未收齐时，这还不是一次请求。

重点
只到达长度的一部分，或载荷还缺字节时，请求数是多少？收齐之后请求数和载荷是什么？

背景
面向连接的协议把请求切成帧。一种常见帧是先放长度，再放那么长的内容。字节流可以在任意位置被分成多次读取。长度或内容还没到齐时，已经到达的字节还不能当成一个请求。

长度只到一半，或内容还差几个字节，请求数保持为 0。都到齐的那一次之后，请求才成立。把没到齐的字节当成一帧，会把下一帧的开头算进来。

语言
长度是网络字节序的 32 位整数。本课的载荷长度是 4，内容是 ping。字节流来自一对已连接的套接字。

机制
一帧由 4 字节大端长度和恰好这么多的载荷字节组成。缓冲区内长度不足 4 字节，或长度已经到齐但载荷字节数还不够时，不产生请求。长度和载荷都到齐后产生一次请求，并只消费这一帧。进程和系统调用的关系见 OS-001。

程序
程序分三次写入这 8 个字节，并在前两次之后检查请求数。

证明
前两段写入之后请求数是 0。第三段写入之后请求数是 1，载荷是 ping。

=== SRV-003
名词
tid 是 Linux 为每个任务分配的标识。一个已接受的连接可以由一个单独的线程读取。

重点
两条连接的 tid 是否都为正数且互不相等？A 和 B 是否都被读到？

背景
一个进程可以同时读多条连接。每条连接由自己的线程读取时，才能把字节归回那条连接。Linux 用来区分线程的标识是 tid。

两条连接的 tid 不同，日志可以按 tid 分开来源。都由同一个线程读走，日志里只有一个 tid，就分不清字节来自哪条连接。

语言
每个连接在自己的线程里调用 syscall(SYS_gettid)，并读取一个字节。

机制
监听套接字接受两个连接。两个线程的 tid 必须不同，两个标记都必须出现。tid 的核对与 OS-003 相同。本课不把 tid 当作 PID 命名空间里的进程号，那是 CTR-001 的事实。

程序
程序记录两个 tid 和两个标记。

证明
两个 tid 都大于 0 且互不相等。标记 A 和 B 都被读到。

=== SRV-004
名词
读期限是程序等待一帧收齐的时间。这里的期限是 poll 的 400 毫秒。

重点
期限内没有发送数据的连接是否被关闭？同一轮里发送完整帧的连接是否收到 OK？

背景
已经收齐一帧的连接可以回答。还在等字节的连接如果没有期限，一个不再发送的连接会把整个读取停住，已经可以回答的连接也跟着停。给未收齐的连接一个截止时间，到期仍未形成一帧就关闭它。

本节核对期限内未收齐的连接是否被关闭，已经收齐的连接是否还能继续。

语言
帧格式与 SRV-002 相同。poll 的等待时间是 400 毫秒。运行器的 timeout_ms 是 20000。

机制
未收齐帧的连接关闭，并计一次超时。载荷为 FAST 的连接得到 OK。这次关闭由程序的 poll 决定。运行器只在实验进程超过 timeout_ms 时写入 timed_out。

程序
程序同时接受两条连接，统计超时次数和回答次数。

证明
超时次数是 1，回答次数是 1，FAST 连接读到 OK。

=== CTR-001
名词
PID 命名空间有自己的进程号。unshare(CLONE_NEWPID) 之后创建的第一个子进程，在新命名空间里是 1 号。

重点
用户命名空间把当前用户映射为 0 之后，第一个子进程的 pid 是不是 1？

背景
Linux 可以用命名空间给一组进程单独的进程号视图。直接建立一个新的 PID 命名空间，常常因为没有权限失败，错误是 EPERM，对应的操作是 unshare(CLONE_NEWPID)。

可以先建立用户命名空间，把调用进程映射成里面的 root，再建立 PID 命名空间。用户命名空间的操作是 unshare(CLONE_NEWUSER)，映射写在 uid_map 和 gid_map。此后新命名空间里的第一个子进程看到的进程号是 1。这个 1 不是宿主机上原来的进程号。

语言
用户命名空间由 unshare(CLONE_NEWUSER) 建立。映射写成 0、当前用户标识、长度 1。随后再 unshare(CLONE_NEWPID)。

机制
映射成功且 CLONE_NEWPID 成功时，子进程的 getpid 为 1。任一步不能完成时，结果为不支持。线程的 tid 见 OS-003，那是另一套标识。

程序
程序检查第一个子进程的退出状态是否表示 pid 为 1。

证明
子进程的 pid 是 1，或者命名空间不能建立并记为不支持。

=== CTR-002
名词
挂载命名空间有自己的挂载树。MS_REC|MS_PRIVATE 使新的挂载留在这棵树里。

重点
tmpfs 上的标记文件，命名空间内能否读回，命名空间外的进程能否看见？

背景
挂载默认可以沿着共享关系出现在父命名空间里。要把容器里新挂的文件系统留在里面，先把已有挂载改成不向外传播。递归地改成私有使用的标志是 MS_REC 和 MS_PRIVATE。

然后再在这个命名空间里挂上内存文件系统并写一个标记。标记只应出现在里面。外面也能看见，说明挂载仍在向外传播。

语言
用户命名空间的映射与 CTR-001 相同。unshare(CLONE_NEWNS) 建立挂载命名空间。tmpfs 挂在 vis 上。

机制
fork 发生在进入新挂载命名空间之前，因此那个进程仍使用原来的挂载树。本进程把 / 设为私有，再把 tmpfs 挂到 vis，并写入 vis/marker。本进程读回 in。命名空间外的进程对这个路径 access 失败。挂载或用户命名空间不能建立时，结果为不支持。

程序
程序比较命名空间内的读结果和命名空间外进程的 access 结果。

证明
命名空间内读到 in。命名空间外的进程看不到 vis/marker。

=== CTR-003
名词
chroot 把进程的路径解析根换到一个准备好的目录。

重点
chroot 之后，/data/token 的内容是什么？/outside 能否打开？

背景
进程解析绝对路径时，从当前的根目录开始。把这个根换成另一个目录的操作是 chroot。换过之后，打开准备目录里的文件，查找落在这棵新树里。

再打开新根以外的绝对路径，查找仍从新根开始，到不了原来的树。chroot 之前已经打开的目录描述符不经过这次解析，仍指向原来的目录。

语言
chroot 之前，程序在私有挂载命名空间中写好 jail/data/token 和目录外的 outside。用户命名空间映射与 CTR-001 相同。

机制
chroot 到 jail 之后，/data/token 解析到该目录中的 token，内容是 inside。/outside 在这棵树里不存在。CTR-002 核对的是挂载是否留在命名空间内。本课核对 chroot 之后 open 的路径。不能完成 chroot 时，结果为不支持。

程序
程序读 /data/token，并尝试打开 /outside。

证明
/data/token 的内容是 inside。/outside 打开失败。

=== CTR-004
名词
RLIMIT_AS 是进程虚拟地址空间的上限。软限制是当前可以使用的上限。

重点
把软限制设为当前 VmSize 加上 64MiB 之后，一页映射和 80MiB 映射的结果分别是什么？

背景
内核对进程地址空间的大小有上限。这项资源限制的名字是 RLIMIT_AS，本节调整的是它的软限制。把软限制调到当前地址空间附近之后，再申请一页仍在余量里，写入可以完成。

再申请一块明显超过余量的长度，映射失败，返回 MAP_FAILED，这块地址没有建立。实验运行器限制的是 CPU 时间，信号是 SIGXCPU，不是这次设置的地址空间上限。

语言
VmSize 来自 /proc/self/status。映射使用 MAP_PRIVATE|MAP_ANONYMOUS。硬限制低于目标软限制，或 setrlimit 失败时，结果为不支持。

机制
软限制等于读取到的 VmSize 加上 64MiB。一页映射写入一个字节。80MiB 映射返回 MAP_FAILED。MEM-007 核对映射建立之后能否读写。运行器的 resource_limit 终止原因来自 SIGXCPU。

程序
程序记录两个 mmap 的结果。

证明
一页映射可以写入。80MiB 映射返回 MAP_FAILED。

=== STO-006
名词
页校验和是由页内 8 个字节算出的整数。读取时重新计算，与页上保存的值比较。

重点
校验和相符时返回什么载荷？改动一个字节且不更新校验和时，是否还返回载荷？

背景
从磁盘读回一页时，页上的字节可能已经和当初写入的不同。写入时把数据和根据数据算出的校验和一起留下。读路径按现在的字节再算一次，与页上保存的值比较。两次一致，才把数据交给后面的步骤。

字节改了、校验和没改，重算对不上，这次读取拒绝交出数据。先把记录交出去再补算，损坏的页会进入后面的查找。

语言
校验和从 0 开始，对每个字节执行 checksum = checksum * 131 + byte。页文件先放 8 个字节，再放这个 32 位整数。fsync 失败时结果为不支持。

机制
载荷 RECORD01 写入并 fsync 后，校验和相符，读取返回这 8 个字节。把第一个字节翻过来并保持旧校验和，再次读取时校验失败，调用方的缓冲区保持原样。页的定位见 STO-002。本课核对校验失败时不返回载荷。

程序
程序先读有效页，再读改过一个字节的页，并检查第二次没有写入调用方缓冲区。

证明
有效页返回 RECORD01。校验和不符时不返回载荷。

=== STO-007
名词
本课的检查点文件保存一幅 8 字节页镜像和它的 lsn。ARIES 的检查点记录脏页表和重做起点，不把整页镜像装回缓冲。

重点
过期的页和一份包含旧记录的日志放在一起时，恢复后的页是什么？

背景
检查点把某一时刻的页和当时的日志序号存下来，恢复就不必从空页重放全部日志。先把这页装回去，页上已经有该序号之前的更新，然后只重放序号更大的记录。

从空白页把全部日志重放一遍，更早的旧记录会盖掉检查点里已经有的内容。完整的模糊检查点还包含脏页表和重做起点。这里的检查点文件只有这一页和序号。

语言
检查点文件是 8 字节页镜像和 8 字节 lsn。日志记录包含 lsn、页内偏移和 4 个字节。fsync 失败时结果为不支持。

机制
磁盘上的页是 8 个点，applied_lsn 为 0。检查点镜像是 KEEP....，lsn 为 1。日志里 lsn 1 在偏移 0 写入 LOST，lsn 2 在偏移 4 写入 TAIL。恢复先装上检查点镜像，再跳过 lsn 小于或等于 1 的记录，然后应用 lsn 2，得到 KEEPTAIL，applied_lsn 为 2。STO-005 用页上的 pageLSN 决定重做，并演示日志截断。本课额外使用一份页镜像作为检查点。它没有 ARIES 的 analysis、redo、undo，也没有补偿日志。

程序
程序读回恢复后的页，并比较 8 个字节和 applied_lsn。

证明
恢复后的页是 KEEPTAIL，applied_lsn 是 2。

=== SRV-005
名词
流水帧是同一段字节流里先后排好的多帧。每一帧仍是 4 字节大端长度加等长载荷。

重点
一次读入两帧再加两个长度字节时，请求有几次，顺序是什么？

背景
一次读取可以带回多帧，也可以停在某一帧的中间。解析要按每一帧自己的长度往前切，切完的才成为请求。剩下的字节不够下一帧时，必须留在缓冲区尾部，等后面的读取补上。

把这次读到的全部字节合成一个请求，两帧会并成一帧。把不够一帧的尾部当成新请求，会用半截长度去解释内容。

语言
帧格式与 SRV-002 相同。本课的两帧载荷是 AAAA 和 BBBB，后面还剩两个 0 字节。

机制
读端把套接字上的字节收齐后按长度切分。收齐的帧各产生一次请求，顺序与字节流一致。不足 4 字节长度加 4 字节载荷的尾部留下，不产生第三次请求。

程序
程序写入 18 个字节并关闭写端，再统计切出的请求和剩余字节。

证明
请求是两次，顺序为 AAAA、BBBB。剩余两个字节。

=== SRV-006
名词
有界队列只保留不超过容量的工作项。容量已满时，新连接得到 BUSY，该项不入队。

重点
容量为 2 时，三条连接里有几条入队，有几条得到 BUSY？

背景
工作队列的容量是它同时能够收下的项数。项数达到容量之后，再来的一项不应入队。调用方得到表示忙的结果，这项也不进入完成集合。这里的结果是 BUSY。

已经满了仍把这项放进去，完成集合里会多出它，队列里的个数也会超过所声明的容量。

语言
每条连接发送一个字节标记，并读取 4 字节回答。回答是 OKAY 或 BUSY。容量是 2。

机制
接受循环按连接顺序处理。队列中少于 2 项时，标记入队并回答 OKAY。已经有 2 项时回答 BUSY，不把标记写入队列。入队的两个标记互不相同，并且都属于 A、B、C。连接与线程的关系见 SRV-003。本课核对的是队列容量。

程序
程序统计入队数、BUSY 数，以及客户端收到的 OKAY 和 BUSY 次数。

证明
入队 2 个不同标记，对应 OKAY。第三个连接得到 BUSY。

=== CTR-005
名词
UTS 命名空间保存自己的主机名。sethostname 修改的是调用进程所在的那一份。

重点
新 UTS 命名空间里的主机名是什么？命名空间外的进程读到的主机名变了没有？

背景
主机名属于进程所在的一套命名空间，这套命名空间称为 UTS。修改主机名的调用是 sethostname，它改的是调用进程当前的那一套。

先进入新的 UTS 命名空间再改名，新名字留在里面。外面的进程仍读到原来的主机名。容器和宿主机如果共用一套 UTS，里面的改名会同时成为外面看到的主机名。

语言
用户命名空间映射与 CTR-001 相同。unshare(CLONE_NEWUTS) 建立 UTS 命名空间。sethostname 的参数是 syslab-ns。

机制
fork 发生在进入新 UTS 命名空间之前。本进程把主机名设为 syslab-ns 并读回这个值。命名空间外的进程读到的仍是进入之前的主机名。用户命名空间或 UTS 命名空间不能建立时，结果为不支持。

程序
程序比较命名空间内的 gethostname 和命名空间外进程的 gethostname。

证明
命名空间内的主机名是 syslab-ns。命名空间外的主机名保持原值。

=== CTR-006
名词
网络命名空间有自己的接口索引。SIOCGIFINDEX 查询的是调用进程所在的网络命名空间。

重点
新网络命名空间里 lo 的索引是否存在？进入之前那块非 lo 网卡的索引是否还在？原命名空间里那块网卡是否仍能索引？

背景
每个网络命名空间有自己的网卡视图。进入新的网络命名空间之后，按接口索引查询，能找到回环接口 lo，找不到进来之前在宿主机上选定的那块外部网卡。查询索引的控制命令是 SIOCGIFINDEX。

/sys/class/net 可能仍挂着原来的 sysfs，旧网卡的名字还在目录里。用这棵目录判断新命名空间里有哪些网卡，会把旧视图当成新的接口表。

语言
用户命名空间映射与 CTR-001 相同。unshare(CLONE_NEWNET) 建立网络命名空间。接口名来自进入之前的 SIOCGIFCONF，并跳过 lo。没有 lo 以外的已配置接口时，结果为不支持。

机制
fork 发生在进入新网络命名空间之前。新命名空间里 lo 的接口索引大于 0，那块非 lo 网卡的 SIOCGIFINDEX 失败。原命名空间里同一名字的索引仍大于 0。CTR-002 核对挂载是否留在挂载命名空间内。本课核对接口索引属于哪个网络命名空间。

程序
程序在新命名空间里查询 lo 和那块网卡，并让命名空间外的进程查询同一块网卡。

证明
新网络命名空间可以索引 lo，不能索引那块网卡。原命名空间仍能索引那块网卡。

# 访问控制
这一线核对所有者读位、符号链接、目录的 search permission，以及最后一段路径上的 O_NOFOLLOW。

=== SEC-001
名词
所有者读位是模式中决定文件所有者能否读取该文件的那一位。

重点
模式 000 时 open 是否返回 EACCES？改成 0644 后读到的字节是什么？

背景
Unix 用文件模式里的权限位决定某类用户能不能读。进程的有效用户就是文件所有者时，检查的是所有者那一组里的读位。这一位为 0，打开失败，错误是 EACCES，内容读不出来。

把模式改成所有者可以读，同一次打开就能读到当初写入的内容。这个进程没有 CAP_DAC_OVERRIDE，不能在读位为 0 时仍打开文件。本节不换成另一个用户，也不检查目录的检索权。

语言
open 的读请求要看调用进程作为所有者时的读权限位。本课的进程是文件所有者，并且没有绕过权限检查的能力。

机制
模式 000 的所有者读位是 0，open(O_RDONLY) 在检查权限时失败，不返回文件描述符，也就读不到 SAFE。chmod 0644 把所有者读位置 1，同一次 open 和 read 得到当初写入的 4 个字节。本课不检查其他用户，也不检查目录的执行位。

程序
程序写入 SAFE，分别在模式 000 和 0644 下 open，并比较 errno 和读回的字节。

证明
模式 000 时 open 返回 EACCES。模式 0644 时读到 SAFE。

=== SEC-002
名词
符号链接保存一条路径。open 会打开这条路径指向的文件。readlink 返回链接里保存的路径，不返回目标文件的字节。

重点
open 一个链接时读到什么？readlink 返回什么？

背景
路径的最后一段可以是符号链接。打开文件时，默认会跟着这段链接走到目标文件，读到的是目标文件里的字节。这条默认行为属于 open。

另有一个调用不跟着走，它返回链接里存放的路径字符串，不是目标文件的内容。这个调用是 readlink。一次读到数据、一次读到路径，是因为一次跟随、一次不跟随。

语言
symlink 建立链接。open 默认跟随链接。readlink 读取链接本身。链接不能建立时，结果为不支持。

机制
路径解析遇到符号链接时，open 继续打开目标文件，所以读到的是目标上的字节。readlink 停在链接上，返回创建时写入的路径 target.bin，长度是 10。本课不检查多层链接，也不把链接本身的内容当成 DATA。访问位的作用见 SEC-001。

程序
程序创建目标文件和链接，open 链接读取 4 字节，再 readlink。

证明
open alias 读到 DATA。readlink 返回 target.bin。

# 采样和帧
这一线核对 packed 与 planar 采样，以及像素地址和行 stride。

=== AV-001
名词
packed 采样把各声道交错放在同一块缓冲里。FFmpeg 的 AV_SAMPLE_FMT_S16 就是这种布局：立体声为 L R L R。本课每个样本是本机字节序的 int16，帧号从 0 计。

重点
帧号 2 的左声道和右声道各是什么？帧号 1 的两个声道是什么？

背景
立体声可以让左右声道在同一块缓冲里交替出现，顺序是左、右、左、右。这种交错称为 packed。FFmpeg 里 16 位有符号整数的这种格式名为 AV_SAMPLE_FMT_S16。帧从 0 编号，某一帧的左声道从“帧号乘以一帧字节数”处开始，右声道紧跟在后。每个样本是本机字节序的 int16。

把某一帧的左右写成不同的值，按这个位置读回仍是这两个值。没写过的相邻帧保持 0。采样率和播放时长不由这些偏移决定。

语言
int16 占 2 字节。帧号 i 的左声道起始偏移是 i * 4，右声道在其后 2 字节。pread 使用这个偏移。

机制
交错布局下，写左声道只覆盖那 2 个字节，不改同一帧的右声道，也不改其他帧。帧号 2 的偏移是 8，帧号 1 的偏移是 4。页偏移的算法见 STO-002，这里的跨距是每帧 4 字节。本课不检查采样率、播放时长或压缩码流。

程序
程序把 4 帧写入文件，再按偏移 8 和 4 读回两个 int16。

证明
帧号 2 的左声道是 1000，右声道是 -3。帧号 1 的两个声道是 0。

=== AV-002
名词
紧密排列的 RGB24 帧里，每个像素占 3 字节。像素 (x, y) 的偏移是 (y * 宽 + x) * 3。

重点
像素 (1,1) 的三个字节是什么？像素 (2,1) 和 (1,0) 是什么？

背景
一幅不留行尾空白的彩色图里，像素的位置由行号、列号、宽度和每个像素的字节数决定。对 24 位颜色，每个像素是连续 3 字节。坐标 (x, y) 从“(y 乘以宽度 + x) 乘以 3”处开始。

只改一个像素，同一行右边和上一行同一列的像素仍从各自的位置开始，保持原值。公式里用宽度代替一行的实际跨距，颜色会写进旁边的像素。从下往上的负跨距这里不检查。

语言
偏移按行优先、像素内按 R、G、B 的顺序。宽和高是 4 和 2，不是系统页长。

机制
(1,1) 的偏移是 (1 * 4 + 1) * 3 = 15，三个字节是 0x11、0x22、0x33。(2,1) 的偏移是 18，(1,0) 的偏移是 3，这两处保持 0。写一个像素不改跨距之外的字节。按页定位见 STO-002，按声道定位见 AV-001。本课不检查色彩空间转换或编码帧。

程序
程序写入这一帧，再按 15、18 和 3 三个偏移各读 3 字节。

证明
像素 (1,1) 是 11 22 33。像素 (2,1) 和 (1,0) 是 0。

# 步骤和工具
这一线核对按名字查表、参数范围、idempotency key、按字节丢掉最旧的整条消息，以及前一步失败后不执行下一步。

=== AG-001
名词
函数调用的运行时拿到名字和参数后查表执行。名字不在表里时不调用函数。本课没有模型，也没有 tool_call_id。

重点
add 4 的返回值和执行计数是什么？未知名字 nope 会不会增加执行计数？

背景
有的运行时不直接写死要调用哪个函数，而是拿到一个名字和参数，再到表里查找。名字在表里，才执行对应函数，返回函数的结果，并记下执行了一次。名字不在表里，函数不执行，执行次数不变。

这一层没有语言模型，也没有调用协议里的 tool_call_id。未知名字仍产生了副作用，说明没找到之后调用仍被执行了。本节的表里只有一个把参数加一的函数。

语言
比较的是名字字符串。未知名字不调用 add_one。

机制
分派扫描工具表。名字等于 add 时调用函数，参数 4 得到 5，计数加 1。名字 nope 没有对应项，函数不被调用，计数保持 1。本课不连接外部模型，也不解析网络请求。

程序
程序先分派 add，再分派 nope，并比较返回值和计数。

证明
add 4 得到 5，执行计数是 1。nope 没有被执行，计数仍是 1。

=== AG-002
名词
上下文窗口会限制一次请求能带上的历史。本课实现的是其中一种裁剪：按消息文本的字节数设上限，超过时丢掉最旧的整条消息，并保留最新一条。它不按 token 估算，也不保留系统提示。

重点
预算 12 字节时，hello、world、!!、xxxx 依次写入后，还剩下哪些消息？

背景
对话上下文能留下的内容有一个上限。这里的上限按消息文本的字节数计算。几条消息的字节加起来不超过上限，它们都留下。

再写入一条使总和超过上限，就从最旧的整条消息开始丢，直到剩下的字节不超过上限。较新的消息留下，最旧的那条不在了。按词数估计、按对话轮次裁剪、总是保留系统提示，是别的丢弃规则。本节丢弃的单位是整条消息。

语言
字节数按每条消息的文本长度相加，不按字符显示宽度。预算是 12。只剩一条消息时，即使它自己超过预算也保留。本课的写入没有走到只剩一条仍超预算的情形。

机制
实际的上下文管理常按完整的一轮对话裁剪，并保留开头的任务说明。本课更窄：只把各条消息的文本长度相加，预算是 12 字节。追加 xxxx 后总长 16，于是丢掉最旧的整条 hello，剩下 world、!!、xxxx，合计 11，最新一条仍在末尾。工具按名字分派见 AG-001。本课不调用模型，也不做 token 计数。

程序
程序按这个顺序追加四条消息，再检查 hello 不在、其余三条在，且总字节数不超过 12。

证明
hello 已丢。剩下 world、!!、xxxx，最新一条是 xxxx。

=== AG-003
名词
工具调用按返回结果决定是否继续。前一步返回失败时，运行时不执行下一步。这是顺序控制，不是一种单独命名的锁。

重点
第一步失败时完成了哪些步骤？第一步成功时完成记录是什么？

背景
多步调用里，后一步使用前一步的结果，所以后一步要等前一步结束。前一步失败，后一步不调用，完成记录里没有任何一步。前一步成功，记录里先写下前一步，再调用后一步，后一步成功后再写下它。

这里没有锁，失败之后不重试，两步也不并行。本节分别让第一步失败和成功。

语言
run 在 step_one 返回 false 时直接返回。step_two 只出现在这次返回之后。

机制
失败路径不调用 step_two，所以列表里没有 two。成功路径先记录 one，再记录 two，顺序固定。本课不重试失败的第一步，也不并行执行两步。上下文预算见 AG-002。

程序
程序用失败和成功两种输入各跑一次，并比较完成列表。

证明
第一步失败时没有完成记录。第一步成功时完成记录是 one、two。

=== SEC-003
名词
目录的执行位表示 search permission，也就是检索权限。path_resolution 在当前查找目录上没有检索权限时返回 EACCES。文件自己的读位不能代替它。

重点
目录模式是 0644 时，里面可读的文件能否打开？改成 0755 之后读到什么？

背景
打开目录里的文件之前，内核要逐级进入路径上的目录。目录允许被进入，靠的是它的执行位。手册 path_resolution(7) 把这个执行位称为 search permission，也就是向下查找的许可。文件自己的读位不能代替它。

目录模式是 0644、所有者没有执行位时，查找停在目录上，打开失败，错误是 EACCES。把目录改成 0755，查找才能进到文件。CAP_DAC_READ_SEARCH 和 CAP_DAC_OVERRIDE 可以绕过，这个进程两者都没有。

语言
穿越目录查找名字需要目录的执行位。0644 给所有者读写，不给执行。0755 给所有者执行。

机制
open 解析 box/item 时，box 是路径前缀里的查找目录。Linux 的 path_resolution 规定：进程对当前查找目录没有 search permission，就返回 EACCES。0644 的第三位是执行/检索位，所有者没有这一位，所以解析停在目录上，不会因为 item 可读而继续。chmod 0755 恢复检索权限后，同一路径读到 DATA。普通文件的读位见 SEC-001。本课只检查所有者类别，不检查 group、other，也不检查符号链接。能力 CAP_DAC_READ_SEARCH 可以绕过这次检查；本课的进程没有这个能力。

程序
程序建立目录和文件，去掉目录执行位后再加回，并比较两次 open 的结果。

证明
目录 0644 时 open 返回 EACCES。目录 0755 时读到 DATA。

=== SEC-004
名词
O_NOFOLLOW 要求路径的最后一段本身就是要打开的文件。最后一段是符号链接时，open 停止并返回 ELOOP。

重点
带 O_NOFOLLOW 打开 alias 得到什么错误？不带这个标志时读到什么？

背景
打开路径时，最后一段若是符号链接，默认会跟着走到目标。若这次打开必须停在链接本身，就要带一个标志，让内核不跟随最后一段。这个标志是 O_NOFOLLOW。不与 O_PATH 一起使用时，打开失败，错误号是 ELOOP。

路径中间的符号链接仍会被跟随。链接层数过多也返回 ELOOP。本节的路径只有最后一段是链接，才能把这个错误归到该标志。本节不描述 O_PATH。

语言
O_NOFOLLOW 只约束路径最后一段。不带它时，open 跟随链接。链接不能建立时，结果为不支持。

机制
open(2) 规定：路径最后一段是符号链接且带 O_NOFOLLOW、不带 O_PATH 时，调用失败，errno 为 ELOOP。更早的路径分量里的符号链接仍然会被跟随。这个 ELOOP 和“解析过程中符号链接过多”用的是同一个错误码，本课的路径只有最后一段是链接，所以这里的 ELOOP 来自 O_NOFOLLOW。去掉该标志后，open 打开目标，读到 DATA。readlink 与跟随的差别见 SEC-002。本课不检查路径中间段，也不使用 O_PATH。

程序
程序创建目标和链接，分别用两种 open 标志打开 alias。

证明
O_NOFOLLOW 返回 ELOOP。不带该标志时读到 DATA。

=== AV-004
名词
planar 采样让每个声道占用自己的 plane。FFmpeg 的 AV_SAMPLE_FMT_S16P 是有符号 16 位平面格式。本课把左 plane 和右 plane 顺序放在同一个文件里，帧号从 0 计。

重点
帧号 2 的左声道和右声道分别在哪个偏移，值是什么？帧号 1 的左声道是什么？

背景
立体声也可以把一个声道的样本全部放在前一段，另一个声道再放在后一段。这种按声道分开放的方式称为 planar。FFmpeg 里 16 位有符号整数的这种格式名为 AV_SAMPLE_FMT_S16P。某一帧的右声道因此在右声道那一段的对应位置，不在左声道的下一个样本。

紧跟着左声道去读右声道，读到的是下一帧的左声道，或左声道那段里的空位。本节用一个文件模拟两个平面，不构造两个 AVFrame。

语言
帧号 i 的左声道偏移是 i * 2。右声道偏移是 8 + i * 2。帧号 2 因此分别在 4 和 12。

机制
FFmpeg 对 planar 的说明是：每个声道在单独的 data plane 里，一个声道的样本不与另一个声道交错。本课只用一个文件模拟两个 plane 的先后顺序：前 8 字节是左声道的 4 个 int16，后 8 字节是右声道。帧号 i 的左样本在 i * 2，右样本在 8 + i * 2。packed 的 L R L R 见 AV-001。本课没有为每个声道使用独立指针，也不检查采样率和播放时长。

程序
程序写入两个平面，再读取偏移 4、12 和 2。

证明
偏移 4 是 1000，偏移 12 是 -3，偏移 2 是 0。

=== AV-003
名词
stride，也叫 pitch，是内存里从一行像素到下一行像素的字节数。有填充时它大于 width * 每像素字节数。本课使用自上而下的正 stride。

重点
stride 为 16、宽为 4、每像素 3 字节时，像素 (0,1) 在哪个偏移？偏移 12 是什么？

背景
图像里从这一行开头到下一行开头的字节数，可以大于“宽度乘以每个像素的字节数”，多出来的是为对齐留下的空白。这个距离称为行跨距，也叫 stride 或 pitch。

下一行因此从跨距那个位置开始，而不是从紧密排到的位置开始。跨距更大时，紧密排法会落到的位置仍是这一行尾部的空白，保持 0。

语言
像素 (0,1) 的偏移等于 stride。width * 3 只是一行像素本身占用的字节数。

机制
像素地址是 base + y * stride + x * bytes_per_pixel。这里 x 为 0、y 为 1、stride 为 16，所以 (0,1) 在偏移 16，第一个字节是 0xAB。width * 3 等于 12，那是没有填充时的行宽，不是本帧的 stride，所以偏移 12 仍是 0。紧密排列、stride 等于 width * 3 的情形见 AV-002。Windows 的 Image Stride 说明还提到自下而上的图像可以使用负 stride；本课只检查正 stride，也不做色彩转换。

程序
程序写入高 2、stride 16 的帧，再读偏移 16 和 12。

证明
偏移 16 是 AB。偏移 12 是 0。

=== AG-004
名词
参数范围在调用工具函数之前检查。add 只接受 0 到 10。

重点
add 4 的结果和执行计数是什么？add 100 和未知名字 nope 会不会增加计数？

背景
按名字调用之前，还可以先检查参数是否在允许的范围内。范围通过，才查找并调用，执行次数增加。范围不通过，调用不会开始，次数不变。名字不存在，同样不会执行。

如果范围判断写在函数体里面，函数已经开始执行，次数会先增加。本节先检查 0 到 10，再决定是否调用。

语言
分派先比较名字，再检查参数。两项都通过才调用 add_one。

机制
名字是 add 且参数在 0 到 10 时，调用把参数加 1，并增加计数。参数 100 在调用前被拒绝。名字 nope 在进入范围检查之前就找不到工具。按名字分派见 AG-001。本课不连接外部模型。

程序
程序依次分派 add 4、add 100 和 nope，并比较返回值与计数。

证明
add 4 得到 5，计数是 1。add 100 和 nope 之后计数仍是 1。

=== AG-005
名词
idempotency key 是一次工具调用的去重键。同一个键再次出现时，返回已经保存的结果，不再执行工具。这个键由调用方提供；只用参数当键会把两次本应分开的调用并成一次。

重点
键 k 第一次 add 4 得到什么？同一键再传入 9 时结果和执行计数是什么？键 m 会怎样？

背景
同一次请求可能因为重试再次到达。调用方另给一个键，用来认出这是不是已经做过的那一次。这个键第一次出现，函数才执行，结果按键留下。同一个键再来，即使参数不同，也返回留下的结果，函数不再执行。

这种键称为幂等键。它必须由调用方提供，不能从参数推算，否则不同请求会共用一个结果。留下的记录只在这个进程里，没有过期时间。

语言
记录按键查找。命中时不读取这次的参数来重算。表里没有这个键时才调用 add。

机制
调用方传入键。第一次见到 k 时用参数 4 计算 5 并保存在本进程的表里。之后同一个 k 即使参数改成 9，也不再进入工具，直接返回 5。m 是另一个键，所以会执行一次。参数范围见 AG-004。记录不写出进程，也没有过期时间。本课不把键解释成消息预算，也不从参数本身派生这个键。

程序
程序以键 k 调用两次，参数分别是 4 和 9，再以键 m 调用参数 4。

证明
键 k 两次都得到 5，其间执行计数保持 1。键 m 执行后计数是 2。
